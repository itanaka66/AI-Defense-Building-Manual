# はじめに

## 本書について

本書は「AI自律型サイバー防御システム 構築マニュアル」前編の第7部です。第6部の最後にテスト版で確かめた「読み取り位置の検証」を本番に反映し、そのうえで、DBの重複処理、巨大な行、JSONの深さ、ファイルディスクリプタ、状態の保存の失敗など、残った異常系を一つずつ検証して仕上げます。

## 本書の表記

- コマンドやファイル内容は、構築時に実際に使用したものをそのまま掲載しています。改変していません。
- 各手順の冒頭に「実行先」を示します。DBの確認は、LXC 109の中でDB管理者（`postgres`）で行います。
- 「実行結果（例）」は構築時の実際の出力です。ハッシュ・件数・時刻・inodeなどは、お使いの環境では異なります。
- テスト用のファイルやスクリプトは `/tmp` に作ります。VMを再起動すると消えることがあります。

# 第3章　実際のDBでの重複処理の試験

## 3.1　考え方

第4部・第6部では、モックの接続で重複処理を試験しました。ここでは、本番のCollectorのコードと実際のPostgreSQL（`wazuh_collector` の権限）を使い、外側のトランザクションの中ですべてを行って、最後に必ずロールバックします。本番のテーブルにテストのデータは残りません。

`connection.transaction()` は、すでにトランザクションの中で呼ばれるとセーブポイントになります。そのため、重複でエラーになっても、そのセーブポイントだけが戻り、同じ接続で次のイベントを処理できるはずです。

| `transaction remains usable after duplicate` | 重複の後もトランザクションが使える |

# 第7章　DBの障害と読み取り位置

## 7.1　run() の処理の順序

本番の `run()` は、1行を読む前に行の先頭の位置（`line_start`）を覚えておき、失敗したときはその位置に戻ります。構築時にコードを読んで確かめた動作は次のとおりです。

| 処理 | 動作 |
|---|---|
| PostgreSQLへの接続の失敗 | 行の先頭に戻し、5秒後に再接続 |
| 登録・処理の失敗 | 行の先頭に戻し、接続を捨てる |
| 状態の保存の失敗 | 行の先頭に戻して、もう一度処理 |
| 重複したイベント | SQLSTATE `23505` として処理済みにする |
| 上限を超えた行 | 状態を保存してから読み飛ばす |

# 第12章　重複の再処理と状態の保存の失敗

## 12.1　設計の確認

構築時にコードを読んで確かめた、登録とローテーションの設計は次のとおりです。

| 項目 | 内容 |
|---|---|
| イベントID | Wazuhのアラートの `id`（128文字まで）。IDのないイベントは拒否 |
| 登録 | 通常の `INSERT`（`ON CONFLICT` は使わない） |
| 状態の保存 | DBへの登録が成功した後 |
| 重複 | SQLSTATE `23505` だけを処理済みにする |
| ローテーション | 新しいファイルのinodeと位置 `0` を先に保存してから切り替える |

DBに登録した後で状態の保存に失敗すると、同じ行をもう一度処理します。そのとき、同じIDのイベントは重複として扱われ、二重に登録されません。

## 12.2　重複の再処理

疑似のDB接続を使い、1回目は登録、同じイベントの再処理は重複として処理済み、次の別のイベントは登録されることを確認します。
