# はじめに

## 本書について

本書は「AI自律型サイバー防御システム 構築マニュアル」中編の第27部です。第25部で監査ログの出力先を設定し、第26部でリクエストの本文を記録しないようにしました。ここでは、設定は変えずに**読み取りだけで**、次のことを確かめます。

1. 監査ログのインデックス（`security-auditlog-YYYY.MM.dd`）ができ、イベントが保存されている
2. 保存されたイベントに、リクエストの本文や認証のヘッダーが入っていない
3. 監査の設定が `.opendistro_security` に保存され、再起動のあとも読み込まれる作りである

本文やヘッダーの「値」は表示せず、項目の名前・件数・長さ・形だけを調べます。

## 本書の表記

- コマンドやプログラムは、構築時に実際に使用したものをそのまま掲載しています。改変していません。
- 実行先は **security-core VM 220（root）** です。
- インデックスの名前 `security-auditlog-2026.11.21` は構築した日のものです。自分の環境の日付に置き換えてください。

## 1.3　yellowの理由

インデックスの状態は `yellow` でした。シャードを確かめます。

⟦C2⟧

| シャード | 状態 |
|---|---|
| プライマリ（p） | `STARTED`（node-1） |
| レプリカ（r） | `UNASSIGNED`（`INDEX_CREATED`） |

⟦C3⟧

ノードは1つ、プライマリのシャード36個はすべて動いており、割り当てられていないのはこのインデックスのレプリカ1つだけでした。ノードが1つなので、レプリカを置く場所がないためです。保存の失敗ではありません。レプリカの数は変えず、`yellow` のままにします（不足情報メモ 27-A）。

⟦C18⟧

⟦C19⟧

# 第4章　集計で確かめる

## 4.1　集計がうまくいかない

⟦C22⟧

⟦C23⟧

⟦C24⟧

# おわりに

第27部で、次のことを確かめました。

| 項目 | 結果 |
|---|---|
| 監査ログの保存 | `security-auditlog-YYYY.MM.dd` に保存されている（構築時 89件） |
| リクエストの本文 | ふつうのイベントには記録されていない |
| `audit_request_body` がある 17件 | 内部の設定の読み取りの固定の形（`{"field_names":[...]}`）だけ |
| 認証のヘッダー | 記録されていない |
| 設定 | `.opendistro_security` に保存され、起動のときに読み込まれる作り |
| インデックスの状態 | ノードが1つのため `yellow`（レプリカを置けない） |

すべての REST の操作・すべてのイベントの種類を試したわけではありません。次の部では、Wazuh のアラートを PostgreSQL に送る Collector を点検します。
