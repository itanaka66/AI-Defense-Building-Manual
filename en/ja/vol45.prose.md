# はじめに

## 本書について

本書は「AI自律型サイバー防御システム 構築マニュアル」第4巻の第45部です。第3巻（第31部〜第44部）で、イベントを保存する PostgreSQL のバックアップと復元を仕上げました。第4巻では、LLM（大規模言語モデル）を使った脅威の分析に進みます。

LLM に防御の操作の権限を直接与えることはしません。LLM は判断の材料と提案を作るだけで、実際の操作とは切り離します。その前提として、LLM に渡すデータの信頼性を確かめます。第45部では次のことを行います。

1. 既存の環境（Wazuh・PostgreSQL・Ollama・AI Defense Manager）の配置と状態を、読み取りだけで確かめる
2. Wazuh Manager の設定ファイル `/var/ossec/etc/ossec.conf` が XML として壊れていることを見つけ、原因を調べる
3. 設定ファイルを控えてから修復し、Wazuh の検査のコマンドで確かめる（Wazuh は再起動しない）

## 第4巻について

第4巻では、AI Defense Manager（VM 230）を中心に、LLM による分析を安全に動かすための仕組みを作ります。LLM に渡す入力を許可リストで絞り、LLM の出力を伏せ字にして承認の判断をサーバーの側に置き、API にトークンによる認証を入れます。さらに、ログの改ざんを見つける仕組み（FSS）を作り、Wazuh のローカルのルールを直して、最後に AI 防御のエージェントを作り始めます。

# 第2章　設定ファイルの壊れた場所を調べる

## 2.1　エラーの位置

> **実行先：pve**

⟦C4⟧

`/var/ossec/etc/ossec.conf` は、**323行目より後に、XML の文書のルート要素の外の内容がある**ため、標準の XML のパーサーで読めませんでした。Wazuh のサービスが `active` でも、設定が正しいとは言えません。

## 2.2　エラーのまわりの構造

値は表示せず、タグの構造だけを見ます。

> **実行先：pve**

⟦C5⟧

321行目で最初のルート要素 `</ossec_config>` が閉じたあと、323行目で2つ目の `<ossec_config>` が始まっていました。最後に足した設定のブロックが、元のルート要素の外に置かれた状態です。

## 2.3　いつからこの状態か

> **実行先：pve**

⟦C6⟧

| 項目 | 結果 |
|---|---|
| `ossec.conf` の更新 | 11月17日 |
| Wazuh Manager の起動の記録 | 11月18日〜22日に毎日 |
| 最後の起動 | 11月22日 21:52 UTC（日本時間 11月23日 06:52） |

壊れた XML のままで、少なくとも11月18日からは Wazuh Manager が起動していました。

## 2.4　足したブロックの中身

> **実行先：pve**

⟦C7⟧

⟦C8⟧

323〜339行目には、2つ目の `<ossec_config>` に囲まれて `<localfile>` が3つありました。

| 対象 | 形式 | 用途 |
|---|---|---|
| journald | journald | systemd の journal |
| `/var/ossec/logs/active-responses.log` | syslog | Wazuh の Active Response の記録 |
| `/var/log/dpkg.log` | syslog | Debian のパッケージの操作の記録 |

これらは消さずに、最初の `<ossec_config>` の中にまとめるのが自然です。その前に、元のブロックに同じ設定がないかを確かめます。

## 2.5　コンソールから確かめる

この時点で、Guest Agent を通したコマンドの実行（`guest-exec`）がタイムアウトするようになりました。VM 220 は `running` で、Guest Agent の ping も通るので、VM 220 の再起動や Guest Agent の入れ直しはせず、Proxmox の画面の **VM 220 → Console** から root でログインして確かめます。

> **実行先：VM 220**

⟦C9⟧

Guest Agent（`qemu-guest-agent`）と Wazuh Manager はどちらも動いていました。

> **実行先：VM 220**

⟦C10⟧

| ブロック | `localfile` の数 | 内容 |
|---|---|---|
| 1つ目（本来のルート要素） | 3 | `command` 1件、`full_command` 2件 |
| 2つ目（323行目より後） | 3 | journald 1件、syslog 2件 |

形式も入力元も違い、重複ではありません。6件すべてを残します。

# 第3章　設定ファイルを修復する

## 3.1　控えてから修復する

次の処理を行います。Wazuh の再起動やサービスの変更はしません。

1. いまの `ossec.conf` を別のファイルに控える
2. 2つ目の `<ossec_config>` の外枠だけを取り除き、中の3件を1つ目のブロックの中に移す
3. XML の構文、設定の件数、SHA256 を確かめる

> **実行先：VM 220**

⟦C11⟧

XML の構文は正常で、`localfile` は6件、控えのファイルの SHA256 は修復の前のファイルと一致しました。Wazuh Manager は動いたままです。

## 3.2　ルート要素・所有者・権限

> **実行先：VM 220**

⟦C12⟧

| 項目 | 結果 |
|---|---|
| `<ossec_config>` の開始・終了 | 各1個 |
| ルート要素 | `ossec_config` |
| `localfile` | 6件 |
| 所有者・権限 | `root:wazuh`（GID 110）・`660` |
| 控え | あり、修復の前の SHA256 と一致 |

## 3.3　Logcollector の設定の検査

Wazuh の `-t` は設定を検査するだけのオプションで、動いているサービスを再起動しません。

> **実行先：VM 220**

⟦C13⟧

`wazuh-logcollector -t` は終了コード `0` でした。`pgrep` の警告は、プロセスの名前が15文字を超えるためにふつうの検索で一致しないという意味で、設定のエラーではありません。

## 3.4　動いているプロセスとログ

> **実行先：VM 220**

⟦C14⟧

⟦C15⟧

| 確かめたこと | 結果 |
|---|---|
