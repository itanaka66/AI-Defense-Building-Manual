# はじめに

## 本書について

本書は「AI自律型サイバー防御システム 構築マニュアル」前編の第9部です。第8部で監視基盤が完成した後、次の段階（SOCデータ統合基盤）に進む前の確認で、Wazuh Collectorが止まっていることが見つかりました。第9部では、その原因を調べ、取りこぼしたアラートをDBに取り込み直して通常の収集に戻し、続けて監視・DB・時刻・イベントの内容を点検して、見つかった問題（多発していたイベント）に対処するまでを扱います。

第7部の「未対応の課題」に書いた「旧ファイルが圧縮された後の再開」が、実際に起きた事例です。

## 本書の表記

- コマンドやファイル内容は、構築時に実際に使用したものをそのまま掲載しています。改変していません。
- 各手順の冒頭に「実行先」を示します。
- 「実行結果（例）」は構築時の実際の出力です。inode・件数・時刻などは、お使いの環境では異なります。
- 状態ファイル（`state.json`）や接続情報の中身を表示するコマンドは載せていません。

# 第2章　2つ目の原因：保存したinodeの消失

# 第3章　復旧の方針と準備

## 3.1　方針

Collectorのソースに圧縮ファイルの対応を加えるのではなく、次の順で復旧します。Collectorのソース・systemdの設定・Wazuhのログ自体は変更しません。

1. 19日分（`ossec-alerts-19.json.gz`）の9,039件を、Collectorの既存の処理（`process_line()`）でDBに登録する。
2. すでに登録済みのイベントは、既存の重複処理（一意制約）で飛ばされる。
3. 全件の処理が終わった場合だけ、状態ファイルを今の `alerts.json` のinode・位置 `0` に進める。
4. Collectorは自動再起動で、今の `alerts.json` の先頭から通常の収集に戻る（保存したinodeが今のファイルなので、ディレクトリの探索は行われない）。

途中で失敗したときは状態ファイルを進めないため、もう一度実行しても重複処理で安全にやり直せます。

## 残った課題

- **【リスク・未対応】** 日付が変わると、Wazuh が新しい `alerts.json` を作ります。新しいファイルに Collector の読み取りACLが付かなければ、同じ停止がまた起きます。毎日のローテーションへの恒久的な対策（既定のACLなど）は行っていません。停止したときは、第1章（ACLの追加）と、必要に応じて第2章〜第4章（取りこぼした分の取り込み）の手順で復旧します。Collectorの状態（`NRestarts` の増加や `PermissionError`）を毎日確認してください。
- **【リスク・未対応】** `alerts` ディレクトリの中の root 専用の隠しディレクトリ（`.acl-inheritance-test.bkv8vd`）は削除しておらず、残ったままです。Collectorが再びディレクトリを探索すると（保存したinodeが今の `alerts.json` でないとき）、同じ権限エラーで止まります。
- Collectorは今も圧縮ファイル（`.json.gz`）を探索の対象にしません。止まっている間に旧ファイルが圧縮されたときは、第2章〜第4章と同じ手順で復旧します。
