# はじめに

## 本書について

本書は「AI自律型サイバー防御システム 構築マニュアル」前編の第2部です。第1部で構築したWazuh環境に、PostgreSQL（LXC 109）のログ監視を加えます。SQL文やユーザー名などをWazuhへ送らずに、認証失敗などのイベントだけを安全に取り出し、送信元IPごとのブルートフォース検知までを構築します。

- PostgreSQLログの調査と、SQL文を転送しない方式の決定（第1章）
- サニタイズフィルターの作成とサービス化（第2〜3章）
- Wazuh Agentの監視設定とManager側の検知ルール（第4〜5章）
- 認証失敗の相関検知（第6章）
- 接続元IPの取得と、送信元IPごとの相関検知の本番化（第7〜8章）

## 本書の表記

- コマンドやファイル内容は、構築時に実際に使用したものをそのまま掲載しています。改変していません。
- 各手順の冒頭に「実行先」を示します。`root@pve` はProxmoxホスト、`root@security-core` はVM 220を表します。LXC 109への操作は、Proxmoxホストから `pct exec 109 --` で実行します。
- 「実行結果（例）」は構築時の実際の出力です。お使いの環境では、件数や日時などが異なります。

# 第1章　PostgreSQLログの調査

この章では、PostgreSQLのログがどこに、どの形式で出力されているかを調べます。PostgreSQLの設定はまだ変更しません。

## 1.1　ログ設定と設定ファイルの確認

**実行先：Proxmoxホスト（root@pve）**

⟦C0⟧

構築時の設定は次のとおりでした。

| 項目 | 設定 |
|---|---|
| log_destination | `stderr` |
| logging_collector | `off` |
| log_directory | `log` |
| log_filename | `postgresql-%Y-%m-%d_%H%M%S.log` |
| ローテーション | 1日 / 10MB |

`logging_collector=off` のため、PostgreSQL自身はログファイルを作っていません。Debianのサービスが標準エラー出力をどこに記録しているかを、次の手順で確認します。

## 1.2　ログファイルとログ出力パラメーターの確認

**実行先：Proxmoxホスト（root@pve）**

⟦C1⟧

確認の結果、次のことがわかりました。

- 監視対象のログファイルは `/var/log/postgresql/postgresql-17-main.log` です。
- 日次ローテーションが動いています。
- `log_line_prefix` は `%m [%p] %q%u@%d ` です。
- `log_connections=off`、`log_disconnections=off`、`log_min_messages=warning` です。接続・切断は記録されていないため、認証失敗や接続異常の監視には制約があります。

## 1.3　ログの内容とWazuhの既存設定の確認

**実行先：Proxmoxホスト（root@pve）**

⟦C2⟧

PostgreSQLのログには、次の種類の行が記録されています。

| 種類 | 内容 |
|---|---|
| `ERROR` | SQLの実行エラー |
| `FATAL` | 認証失敗などの重大なエラー |
| `LOG` | 接続・切断やデータベース内部のイベント |
| `STATEMENT` | 実行されたSQL文 |

Wazuhには、PostgreSQL専用のデコーダーやログ収集設定はありませんでした。

> **重要：** 現在のログには、実際のSQL文やアプリケーションのデータ内容まで記録されています。このログをそのままWazuh Managerに転送すると、データベースの情報がSIEM側にも複製されてしまいます。

## 1.4　監視方式の決定

次の方式で構築することにしました。

**SQL文やパラメーター値をWazuh Managerへ転送しない方式**

1. 生のログはLXC 109の中だけに保持する。
2. LXC 109の中で動く独立したフィルターがログを読み、許可したイベントだけを別のファイルに書き出す。
3. Wazuh Agentは、フィルターが書き出したファイルだけを監視する。

フィルターがWazuhに渡すのは、発生時刻・重大度・あらかじめ決めたイベント分類だけです。SQL文、`STATEMENT`・`DETAIL`・`CONTEXT` 行、ユーザー名、エラーの生メッセージは転送しません。

# 第3章　フィルターの作成とサービス化

## 3.1　フィルターの処理方針

1. PostgreSQLのログを読み取る。
2. 行の先頭にあるPostgreSQL標準のログ形式（日時・PID・重大度）だけを解析して、`FATAL`・`ERROR`・`WARNING`・`PANIC` を判定する。本文中の「ERROR」という文字列は判定に使わないため、SQL文や複数行の `STATEMENT` を誤ってイベントとして扱うことはない。
3. 認証失敗は専用のイベントに分類する。
4. SQL文、`STATEMENT`・`DETAIL`・`CONTEXT`、ユーザー名、エラー本文は出力しない。
5. 起動時点より前の過去ログは転送せず、新しいログだけを処理する。
6. ファイルの交換と、`copytruncate` によるファイルの切り詰めに追従する。

# 第6章　認証失敗の相関検知

| 項目 | 設定 |

| 集計単位 | 同一Agent |
| 時間枠 | 60秒 |
| 発生回数 | 5回 |
| 相関ルールID | `100106` |
| レベル | 12 |

# 第7章　接続元IPの取得とIP対応フィルターの試作

第6章の相関検知は同じAgent単位のため、攻撃元のIPアドレスまではわかりません。この章では、「SQL文・ユーザー名をWazuhへ送らない」方針を保ったまま、認証失敗イベントに接続元IPを加える準備をします。

## 7.2　採用する方式

PostgreSQLの `log_connections` を有効にし、次の仕組みでIPを取得します。

1. PostgreSQLは、接続を受け付けたときに「PID」と「接続元IP」を含む行（`LOG: connection received`）を記録する。
2. 同じ接続で認証に失敗すると、同じPIDで認証失敗の行が記録される。
3. フィルターはPIDとIPの対応をメモリー上だけに一時的に持ち、認証失敗のイベントに接続元IPを付ける。

IPが取得できなかった認証失敗は、IPごとの相関には使わず、これまでどおり単発の検知だけを行います。
