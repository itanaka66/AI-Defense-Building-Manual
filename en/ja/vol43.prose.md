# はじめに

## 本書について

本書は「AI自律型サイバー防御システム 構築マニュアル」第3巻の第43部です。第42部までで、3つの定期の処理（PostgreSQL の論理バックアップ 02:00、LXC 109 のバックアップ 03:00、TrueNAS の ZFS のスナップショット 04:00）を用意しました。ここでは、11月23日の朝に最初の定期の実行の結果を確かめたところで見つかった、2つの別々の問題を直します。

| 問題 | 起きたこと | 原因 | 対策 |
|---|---|---|---|
| 1 | 06:50 に Proxmox が再起動したあと、NFS がマウントされていなかった | NFS のマウントが、TrueNAS の VM 100 が起動する前に始まり、90秒でタイムアウトした | TrueNAS の起動と NFS の応答を待ってからマウントするサービスを足す |
| 2 | 03:00 の LXC 109 のバックアップが `Permission denied` で失敗した | 非特権の LXC のファイルを読む `tar` は UID 100000 で動くが、一時ディレクトリが root だけの NFS の `dump/` の下に作られた | ジョブ `lxc109-daily` の一時ディレクトリを、Proxmox のローカルの `/var/tmp` にする |

02:00 の PostgreSQL のバックアップは成功していました。

## 本書の表記

- コマンドやプログラムは、構築時に実際に使用したものをそのまま掲載しています。改変していません。
- 実行先は、各手順の「実行先」に示します。
  - **pve**：Proxmox のホスト（root）
- TrueNAS の API のコマンドは、実行のたびに TrueNAS の root のパスワードを聞かれます。端末に入力し、ほかには書かないでください。

# 第2章　NFS がマウントされなかった原因

## 2.1　TrueNAS とログ

> **実行先：pve**

⟦C2⟧

TrueNAS への ping は損失0%、RPC（NFSv3・mountd）は応答し、`/mnt/backup` を公開していました。TrueNAS の API も `HTTP 200` でした。TrueNAS 全体や NFS のサービスが止まっているわけではありません。

> **実行先：pve**

⟦C3⟧

カーネルのログから、**Proxmox のホストが 11月23日 06:50:22 ごろに起動し直していた**ことがわかりました。

## 2.2　起動のときのネットワーク

> **実行先：pve**

⟦C4⟧

`networking.service` は 06:50:27 に終わり、`network-online.target` も同じ時刻に届いていました。物理の NIC `eno1` のリンクが上がったのは 06:50:29 で、マウントの開始はその約2秒前でした。

## 2.3　ホストの負荷

> **実行先：pve**

⟦C5⟧

ロードアベレージは約137、64個の論理 CPU に対して実行待ち（`vmstat` の `r`）が132〜146ありました。I/O 待ちは 0% で、目立っていたのは VM 101（`ollama-gpu`）と、その中で動く複数の `llama-server` でした。構築の記録では、ここで負荷の高すぎた LXC を止め、ロードアベレージは 39 まで下がりました。NFS の問題とは別の話として扱います。

## 2.4　TrueNAS の VM が起動した時刻

> **実行先：pve**

⟦C6⟧

⟦C7⟧

| 時刻 | できごと |
|---|---|
| 06:50:27 | `network-online.target` に届き、NFS のマウントを始めた |
| 06:50:29 | `eno1` のリンクが上がった |
| 06:51:57 | NFS のマウントが90秒でタイムアウト |
| 06:54:12 | TrueNAS の VM 100 が起動 |
| 07:21:17 | `pve-guests.service` が全部のゲストを起動し終えた |

NFS のマウントを始めたとき、**保存先の TrueNAS の VM はまだ起動していませんでした**。これがタイムアウトの直接の理由です。

## 2.5　対策の方針

`pve-guests.service` の完了を待つ方式は使いません。今回の起動ではゲストを全部起動するまでに約29分かかり、バックアップの保存先を使えるまでが遅くなりすぎるからです。また、VM の起動の処理が終わっても、TrueNAS の中の NFS が使えるようになるまでには時間がかかります。そこで次のようにします。

1. マウントの前に、TrueNAS の VM 100 が起動しているかを確かめる
2. 起動するまで待つ
3. TrueNAS の NFSv3 の RPC（mountd と NFS）が応答するまで繰り返す
4. 両方が応答したときだけ、マウントする
5. 決めた時間（900秒）の中で用意ができなければマウントを失敗させる。`is_mountpoint 1` によって、ローカルのディレクトリに間違えて書き込むことは防がれたまま

# 第4章　LXC 109 のバックアップが失敗した原因

## 4.1　前回の成功との違い

> **実行先：pve**

⟦C13⟧

ログでは、バックアップの `tar` が次のユーザー名前空間で動いていました。

⟦C14⟧

LXC 109 は非特権のコンテナ（`unprivileged: 1`）なので、コンテナの中の root はホストでは UID・GID `100000` になります。一方、NFS の `dump/` は第42部で次のようにしていました。

⟦C15⟧

## 4.2　UID 100000 で書き込めるか

権限は変えずに、UID・GID `100000:100000` で一時ファイルを作れるかを試します。

> **実行先：pve**

⟦C16⟧

`cannot create` になり、UID 100000 からは `dump/` に入れないことを確かめました。

## 4.3　TrueNAS の ACL と NFS の共有

TrueNAS CORE 12 では、ACL の取得は POST で呼び出します。読み取りだけで、ACL は変えません。

> **実行先：pve**

⟦C17⟧

`/mnt/backup` も `/mnt/backup/dump` も `acltype: NFS4`、所有者は `0:0` でした。`dump` は owner@ 以外にディレクトリを通る権限（`EXECUTE`）がありません。

> **実行先：pve**

⟦C18⟧

⟦C19⟧

NFS の共有は `maproot_user = root`（クライアントの UID 0 だけをサーバーの root にする）、`mapall_user` は空でした。UID 100000 は root として扱われません。

## 4.4　失敗したときのログ

> **実行先：pve**

⟦C20⟧

ログから、失敗していたのはアーカイブの書き込み先ではなく、`tar` が読み込む**一時ディレクトリ**だとわかりました。

⟦C21⟧

Proxmox は、非特権の LXC のファイルを読む `tar` を、UID・GID 100000 にした名前空間の中で動かします。一時ディレクトリは保存先の `dump/` の下に作られ、`dump/` が root だけの `0700` なので、UID 100000 はそこに届きません。一方、最終のアーカイブ（`.tar.dat`）はパイプの出力先で、ホストの root が開くので問題になりません。

したがって、TrueNAS の所有者・ACL・NFS の共有を変える必要はありません。**一時ディレクトリだけをローカルのディスクに置けば**よいことになります。

## 4.5　ジョブごとに一時ディレクトリを指定できるか

> **実行先：pve**

⟦C22⟧

`/var/tmp` は Proxmox のローカルの ext4 の上にあり、空きは約 66GB です。一時ディレクトリには主に LXC の設定のファイルが置かれるので、バックアップの本体の容量は要りません。

> **実行先：pve**

⟦C23⟧

バックアップのジョブの更新の API（`update_job`）は、共通の設定（`json_config_properties()`）から `tmpdir` を取り込んでいて、**ジョブごとに `tmpdir` を指定できる**ことを確かめました。`/etc/vzdump.conf` の全体の設定にしなくても、`lxc109-daily` だけを変えられます。

# おわりに

第43部で、11月23日に見つかった2つのバックアップの問題を直しました。

| 項目 | 結果 |
|---|---|
| PostgreSQL の 02:00 のバックアップ | 成功（17個、チェックサム `OK`） |
| 再起動のあとの NFS | `truenas-nfs-ready.service` で TrueNAS の VM 100 の起動と NFSv3 の応答を待ってからマウントするようにした。マウントの試験は合格 |
| LXC 109 の 03:00 のバックアップ | 原因は、UID 100000 の `tar` が NFS の上の一時ディレクトリに届かないこと。ジョブに `tmpdir: /var/tmp` を設定し、やり直して成功 |
| TrueNAS の所有者・ACL・NFS の共有 | 変えていない |
| 別の課題 | `windows_d/windows_d` の VG のエラー、thin pool の容量の警告（設定は変えていない） |

次の第44部では、Proxmox がバックアップを正しく認識しているかを確かめ、復元したデータベースを本番と細かく比べます。
