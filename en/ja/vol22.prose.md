# はじめに

## 本書について

本書は「AI自律型サイバー防御システム 構築マニュアル」前編の第22部です。第14部〜第21部で作った Wazuh → Relay → AI Defense Manager のつながりを、設定は変えずに**読み取りだけで**点検します。

| 点検の対象 | 場所 |

| Indexer の読み取り専用ユーザー（認証・検索の権限・返る項目） | VM 220 |

# 第2章　Relayの側

## 2.1　サービス

> **実行先：VM 220**

⟦C7⟧

構築時は Ubuntu 24.04.5 LTS で、`ai-defense-relay.service` は `active (running)`、VM 230（`192.168.0.33`）からの要求は `200` で記録されていました。

## 2.2　プログラム

⟦C8⟧

確かめられた安全のための対策は次のとおりです。

- 接続元を `192.168.0.33` に限る
- Bearer トークンを `hmac.compare_digest()` で比べる
- Indexer への接続も CA 証明書で TLS を検証する
- Indexer の検索の件数と期間を制限する
- `_source` と `sanitize_alert()` の両方で、返す項目を限る（`full_log` や任意の `data` は返さない）
- `POST`・`PUT`・`DELETE` などの変更の要求を断る。TLS 1.2 より古いものを断る
- 同時に処理する要求は8つまで。Indexer の応答は 2MiB まで
- エラーの応答に、内部の例外や認証の情報を入れない

> **注意**　構築時に表示された relay.py には、第14部 4.1〜4.3 の内容に加えて、アクセスのログを「接続元のIPアドレスとステータス」だけにする変更と、同時に処理する要求を8つまでにする変更（`threading.BoundedSemaphore(8)`）が入っていました。この変更の手順は構築の記録にありません（不足情報メモ 14-A）。

## 2.3　サービスの定義

⟦C9⟧

専用のユーザー（root ではない）で動き、秘密の情報は `LoadCredential` で渡し、特権を持たず、ファイルシステムは原則として読み取り専用、メモリやタスクの数にも上限があります（第14部 5.1）。

## 2.4　待ち受け

⟦C10⟧

| サービス | 待ち受け |
|---|---|
| Relay | `192.168.0.220:8765`（決めたIPだけ） |
| Wazuh Indexer | `127.0.0.1:9200`（ローカルだけ） |

Indexer にはほかのホストから直接つなげず、Relay を通す作りになっています。

⟦C11⟧

構築時、VM 220 の UFW は無効でした。Relay は決めた IP だけで待ち受け、アプリでも接続元を限っていますが、ネットワークの層での制限は別のものです。UFW を有効にすると Wazuh などの通信に影響するおそれがあるため、ここでは変えません（不足情報メモ 22-A）。

## 2.5　秘密の情報の権限

⟦C12⟧

`/etc/credstore` は `700 root:root`、中のファイルはすべて `600 root:root` でした。
