# はじめに

## 本書について

本書は「AI自律型サイバー防御システム 構築マニュアル」後編の第37部です。第36部の点検で、PostgreSQL のバックアップがないことがわかりました。ここでは、PostgreSQL が動いている **LXC 109** を Proxmox の `vzdump` でバックアップし、**別の番号の LXC（110）に戻して**、PostgreSQL が起動し、データを読めることを試します。本番の LXC 109 には手を加えません。

1. Proxmox の側のバックアップの設定と、保存できる場所を調べる
2. LXC 109 を `snapshot` の方式でバックアップする
3. アーカイブが壊れていないこと、Proxmox がバックアップとして認めることを確かめる
4. LXC 110 に戻し、ネットワークを切ったまま起動して、PostgreSQL とデータを確かめる
5. 試験の LXC 110 を消す

## 本書の表記

- コマンドやプログラムは、構築時に実際に使用したものをそのまま掲載しています。改変していません。
- 実行先は、各手順の「実行先」に示します。
  - **pve**：Proxmox のホスト（root）

# 第1章　Proxmox の側を調べる

## 1.1　実行する場所を確かめる

ここからのコマンドは Proxmox のホストで実行します。PostgreSQL のサーバー（`root@postgresql`）で実行すると、`pvesm: command not found` などになります。まずホスト名を確かめます。

> **実行先：pve**

⟦C0⟧

`pve` と表示されることを確かめてから進めます。

## 1.2　バックアップのジョブとストレージ

⟦C1⟧

バックアップのジョブは `--- []`（0件）でした。`qm config 151` は何も表示しませんでした（151 は IP アドレスの末尾で、VM の番号ではないためです）。

> **メモ**：`pvesm status` では、毎回 `no such logical volume windows_d/windows_d` という LVM のエラーが出ます。今回の作業とは別の問題で、ここでは直しません。

⟦C2⟧

VM は 100（TrueNAS）・101（ollama-gpu）・102・104・126・220（security-core）・230（ai-defense-manager）で、PostgreSQL のサーバーは VM ではありません。PostgreSQL は **LXC 109** で動いています。

## 1.3　LXC 109 の設定

⟦C3⟧

| 項目 | 値 |
|---|---|
| ディスク | `local-lvm:vm-109-disk-0`、50G |
| 種類 | 非特権の LXC（`unprivileged: 1`） |
| 追加のマウント | なし |
| IP アドレス | 192.168.0.151/24 |
| 自動の起動 | `onboot: 1` |

## 1.4　バックアップを置ける場所

⟦C4⟧

`backup` を置けるストレージは `local`（`/var/lib/vz`）だけでした。`local-lvm`・`RAID_A`・`RAID_B` などは、VM や LXC のディスク用です。

⟦C5⟧

`local` の実体は Proxmox のルートのファイルシステム（`/dev/mapper/pve-root`、94G のうち空き 68G）で、`/var/lib/vz/dump/` は空でした。

⟦C6⟧

LXC 109 は 49G のうち 1.7G を使い、PostgreSQL のデータは 473M でした。`local` に置く容量は足ります。ただし、`local` は Proxmox のルートと同じ場所なので、そのディスクが壊れたときの備えにはなりません（第38部で別の保存先を用意します）。

# 第2章　バックアップの方式

## 2.1　vzdump の説明

> **メモ**：`vzdump --help` は `Unknown option: help` になります。説明は `man vzdump` で読みます。

⟦C7⟧

⟦C8⟧

説明のファイルは `/usr/share/man/man1/vzdump.1.gz`、Proxmox VE は `pve-manager/8.4.20` でした。主な選択肢を抜き出します。

⟦C9⟧

| 選択肢 | 意味 |
|---|---|
| `--mode snapshot` | ストレージのスナップショットから作る。LXC はスナップショットを作るあいだ少し止まる（完全に止まらないわけではない） |
| `--mode suspend` / `stop` | 一時停止 / 停止して作る |
| `--compress zstd` | zstd で圧縮する |
| `--storage` | 保存先 |

LXC の `snapshot` は、ディスクがスナップショットのできるストレージにあることが条件です。

## 2.2　local-lvm がスナップショットできるか

⟦C10⟧

`local-lvm`（LVM-thin）は `active` で、約833GB のうち約514GB（61.66%）を使っていました。LVM-thin はスナップショットができます。

⟦C11⟧

`pve/data` のデータの使用率は 61.66%、メタデータは 2.18% で、余裕があります。なお、`local` と `local-lvm` はどちらも同じ NVMe（`/dev/nvme0n1p3`）の上にあります。

# 第3章　LXC 109 をバックアップする

構築時は、実行する前に承認を取りました。保存先は `local`、方式は `snapshot`、圧縮は `zstd`、古いバックアップは消しません（`--remove 0`）。スナップショットを作るあいだ、LXC 109 は少し止まります。

> **実行先：pve**

⟦C12⟧

⟦C13⟧

17秒で終わり、`/var/lib/vz/dump/vzdump-lxc-109-2026_11_22-13_25_49.tar.zst`（約472MB）ができました。

> **メモ**：LVM-thin から、「thin pool があふれないようにする自動の拡張が有効でない」「thin volume の割り当ての合計が実際の容量を超えている」という2つの警告が出ます。バックアップの失敗ではありませんが、容量の管理の課題です（第38部で調べます）。

# 第4章　バックアップを確かめる

| 項目 | 結果 |
|---|---:|
| 大きさ | 495,442,661 バイト |
| zstd の検査 | 成功（0） |
| tar の一覧 | 成功（0） |
| 中のファイルの数 | 37,918 |

## 4.2　PostgreSQL のデータが入っているか

⟦C15⟧

`./var/lib/postgresql/17/main/base/…` と `./etc/postgresql/…` が入っていました。最初の `pvesm extractconfig` は `unable to parse volume ID` になります。このコマンドは、ファイルのパスではなく Proxmox のボリューム ID（`local:backup/ファイル名`）を受け取るためです。

## 4.3　Proxmox がバックアップとして認めるか

⟦C16⟧

ボリューム ID で LXC 109 の設定（ホスト名 `postgresql`、2コア、4GB、50GB、192.168.0.151、非特権）を読み出せました。一覧には、このバックアップのほかに `13_22_41` と `13_24_39` のバックアップもあり、全部で3つでした。どれも消さずに残します。

# 第5章　LXC 110 に戻して試す

構築時は、新しい LXC を作って容量を使うため、実行する前に承認を取りました。

## 5.1　番号と容量

⟦C17⟧

`CTID_110=FREE` で、`local-lvm` には約319GiB の空きがありました。

## 5.2　戻す

バックアップには本番と同じ IP アドレス（192.168.0.151）が入っています。重ならないよう、MAC アドレスを新しく作り（`--unique 1`）、ネットワークのリンクを切り（`link_down=1`）、IP は付けず、戻したあとすぐには起動しません（`--start 0`）。

⟦C18⟧

⟦C19⟧

約1.7GiB を読み込み、LXC 110 ができました。

## 5.3　ネットワークの設定を確かめる

⟦C20⟧

LXC 110 は止まっていて、MAC アドレスは新しくなっていました。ところが、**`net0` の IP がバックアップの中の値（192.168.0.151 と本番と同じ IPv6）に戻っていて、`onboot: 1` でした。** 戻すときに付けた `--net0` が、バックアップの中の設定と合わさったときに上書きされたためです。**LXC 110 はまだ起動しません。** LXC 110 だけを直します（本番の LXC 109 には触りません）。

## 5.4　起動して PostgreSQL を確かめる

⟦C24⟧

`status: running` になりました。ネットワークは切ってあるので、本番の LXC 109 と IP アドレスはぶつかりません。

⟦C25⟧

`postgresql@17-main` は `active`、クラスター `17/main`（ポート 5432）は `online` で、checkpointer・walwriter・autovacuum などのプロセスも動いていました。**バックアップから戻したデータで、PostgreSQL 17 が起動しました。**

## 5.5　データを読む

⟦C26⟧

LXC 110 の `security_workbench`（26MB）の `incident.alert_events` は 55,867 件（異なる ID も 55,867 件）、最も古いイベントは 2026-11-17 20:14:42、最も新しいのは 2026-11-22 04:21:28 でした。本番の LXC 109 と比べます（読み取りだけ）。

⟦C27⟧

| 項目 | 戻した LXC 110 | 本番の LXC 109 |
|---|---:|---:|
| 件数 | 55,867 | 55,869 |
| 異なる ID | 55,867 | 55,869 |
| DB の大きさ | 26MB | 26MB |
| 最も古いイベント | 同じ | 同じ |
| 最も新しいイベント | 04:21:28 | 04:52:28 |

違いは2件で、バックアップを取ったあとに本番に入ったイベントの分です。**バックアップから実際に復元できることを確かめられました。**

# 第6章　試験の LXC を消す

## 6.1　止める

⟦C28⟧

LXC 110 は `stopped`、本番の LXC 109 は `running` でした。

## 6.2　消す

LXC 110 は試験が済んだので、50GB の割り当てを返すために消します（構築時は、消すか残すかを確かめ、消すことにしました）。消すのは LXC 110 だけで、バックアップの3つは消しません。

⟦C29⟧

LXC 110 は止まっているので、`--force`・`--purge`・`--destroy-unreferenced-disks` は付けずに消します。

⟦C30⟧

⟦C31⟧

⟦C32⟧

LXC 110 は `Configuration file 'nodes/pve/lxc/110.conf' does not exist`（消えた）、LXC 109 は `running`、バックアップは3つとも残っていました。

# おわりに

第37部で、LXC 109 をバックアップし、復元できることを試しました。

| 項目 | 結果 |
|---|---|
| バックアップ | `vzdump-lxc-109-2026_11_22-13_25_49.tar.zst`（`local`、snapshot、zstd、17秒、約472MB） |
| アーカイブの検査 | zstd・tar とも成功、37,918 ファイル |
| Proxmox の認識 | ボリューム ID で設定を読み出せた |
| 復元の試験 | LXC 110 に戻し、ネットワークを切って起動。PostgreSQL 17 が起動し、55,867 件を読めた |
| 本番との差 | 2件（バックアップのあとに入った分） |
| あと片付け | LXC 110 を消した。バックアップ3つは残した |

残っている課題は次の3つです。

1. バックアップが本番と同じ NVMe の上にあり、ディスクが壊れたときの備えになっていない
2. 定期のバックアップと世代の管理がない
3. LVM-thin の自動の拡張の保護がない

次の第38部では、LVM-thin の容量を調べ、TrueNAS をバックアップの保存先にする準備をします。
