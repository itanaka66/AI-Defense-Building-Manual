# はじめに

## 本書について

本書は「AI自律型サイバー防御システム 構築マニュアル」後編の第31部です。中編の第30部の最後で、Collector の読み取りの処理を確かめたあと、Wazuh のアラートのログがどう切り替わるか（ローテーション）を調べ始めました。ここではその続きとして、次のことを行います。

1. Wazuh のアラートのログが、いつ・どのように切り替わるかを読み取りだけで調べる
2. 11月21日の切り替えのあと、Collector が新しいファイルを開けず `PermissionError` を出し続けていた原因を突き止める
3. 日付ごとのディレクトリ（`2026`、`2026/Nov`）に **Default ACL**（新しく作られるファイル・ディレクトリに引き継がれる ACL）を足す
4. 一時ファイルで、ACL が引き継がれることを試し、実際の切り替えの前の状態を記録する

わかった原因は次のとおりです。

- アラートのファイルは `alerts/2026/Nov/ossec-alerts-21.json` のように日付ごとに作られ、`alerts.json` はそのファイルへのハードリンク（同じ inode）になっている
- `/var/ossec/logs/alerts` には Default ACL があるが、その下の `2026` と `2026/Nov` には Default ACL がなかった
- そのため、日付が変わって新しいファイルが作られると、Collector のユーザー（`wazuh-collector`）に読み取りの権限が付かなかった

# 第1章　ログの切り替えの方式を調べる

## 1.1　logrotate の設定

> **実行先：VM 220**

OS の logrotate に、Wazuh のアラートのログの設定があるかを探します。

⟦C0⟧

`/etc/logrotate.d` に `alerts.json` を対象にした設定はなく、`copytruncate`（ファイルを切り詰める方式）の設定もありませんでした。アラートのログは、OS の logrotate ではなく Wazuh 自身が切り替えています。

## 1.2　アラートのファイルの一覧

⟦C1⟧

`alerts` の直下には `alerts.log`（inode 5409380）と `alerts.json`（inode 5409517）だけがありました。サブディレクトリまで含めて見ます。

⟦C2⟧

次のことがわかりました。

- 17日〜20日のログは `2026/Nov/ossec-alerts-17.json.gz` のように圧縮されている（`.sum` も付く）
- `alerts.json` と `2026/Nov/ossec-alerts-21.json` は同じ inode（5409517）で、ハードリンクになっている

切り替わった古いログは、ふつうの `.json` としては残りません。

## 1.3　古い inode が見つからないときの Collector の動き

⟦C3⟧

`open_initial_file()` は、保存してある inode が今のファイルと違うとき、圧縮されていない `.json` から古い inode を探し、見つかればその位置から読み直します。見つからなければ例外を出して止まり、**今のファイルの最後へ黙って飛ばすことはしません**。データを飛ばさない安全側の作りです。

## 1.4　Wazuh の切り替えの設定

|---|---|---|
| `monitord.day_wait` | 10 | 切り替え・圧縮・署名の前に10秒待つ |
| `monitord.compress` | 1 | 圧縮する |
| `monitord.sign` | 1 | 署名する |
| `monitord.rotate_log` | 1 | ふつうのログと JSON のログを毎日切り替える |

⟦C8⟧

## 2.2　ACL を確かめる

⟦C9⟧

`/var/ossec/logs/alerts` には Default ACL（`default:user:wazuh-collector:r-x` など）があり、今のファイル（`alerts.json` と `ossec-alerts-21.json`）には `user:wazuh-collector:r--` が付いていました（第29部で付けたものです）。ただし、日付ごとのファイルが作られるのは `2026/Nov` の中です。

⟦C10⟧

`2026` と `2026/Nov` には、ふつうの ACL（`user:wazuh-collector:r-x`）はありましたが、**Default ACL がありませんでした**。このため、`2026/Nov` の中に新しく作られるファイルには、Collector の読み取りの権限が引き継がれません。

## 2.3　ファイルを作っているプロセス

⟦C11⟧

`wazuh-analysisd`（PID 1701）と `wazuh-monitord`（PID 1873）は、どちらも `wazuh` のユーザーで動いていました。どちらがファイルを開いているかを見ます。

⟦C12⟧

⟦C13⟧

⟦C14⟧

# 第3章　Default ACL を足す

`2026` と `2026/Nov` に、次の Default ACL を足します。ふつうの ACL は変えず、新しく作られるものへの引き継ぎだけを足します。Wazuh の再起動も要りません。

| 対象 | 引き継ぐ権限 |
|---|---|
| 所有者 | `rwx` |
| `wazuh-collector` | `r-x`（読み取りと通過だけ。書き込みはなし） |
| グループ | `r-x` |
| その他 | なし |

ファイルは `0640` で作られるため、マスクによって `wazuh-collector` の実際の権限は `r--` になります。

# おわりに

第31部で、ログの切り替えのあとに Collector が新しいファイルを読めなくなる原因を突き止め、対策しました。

| 項目 | 結果 |
|---|---|
| 切り替えの方式 | Wazuh（`wazuh-monitord`）が毎日 00:00:10 ごろに切り替え、古いログは `.json.gz` に圧縮 |
| `alerts.json` | 日付ごとのファイル（`2026/Nov/ossec-alerts-DD.json`）へのハードリンク |
| 止まった原因 | `2026`・`2026/Nov` に Default ACL がなく、新しいファイルに Collector の読み取りの権限が付かなかった |
| 対策 | `2026`・`2026/Nov` に Default ACL を足した（Collector は `r-x`、書き込みなし） |
| 試験 | 新しいファイル・新しい月のディレクトリとも、Collector のユーザーで読めた |
| 切り替えの前 | 読み残し 0、`NRestarts=0`、PostgreSQL への保存も続いている |

次の第32部では、実際の切り替えのあとに Collector が新しいファイルを読めたことを確かめ、過去に保存されなかったイベントを復旧します。
