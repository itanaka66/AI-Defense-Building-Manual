# はじめに

## 本書について

本書は「AI自律型サイバー防御システム 構築マニュアル」第4巻の第53部です。第52部で、VM 230 が実際の Wazuh のアラートを受け取れるようになりました。LLM の分析に進む前に、VM 230 の中で、受け取ったアラートが分析・保存・防御の提案へどうつながるかを、読み取りだけで点検します。

1. イベントの変換から AI の分析までの処理の流れを追う
2. API から保存・防御の操作の提案までの経路と、外への公開・DB の権限を確かめる
3. systemd による隔離の設定を確かめる
4. 伏せ字の処理を、合成したデータで試す
5. LLM の出力が保存・返却されるところの安全を点検する

実際のアラートの取り直し・DB へのアクセス・Ollama の推論・設定の変更・サービスの再起動はしません。

## 本書の表記

- コマンドやプログラムは、構築時に実際に使用したものをそのまま掲載しています。改変していません。
- 実行先は、各手順の「実行先」に示します。
  - **VM 230**：ai-defense-manager（root）

# 第1章　処理の流れ

## 1.1　関数と呼び出しの関係

> **実行先：VM 230**

⟦C0⟧

独立した `event_service.py` は無く、主に次の2段で処理されていました。

1. `wazuh_relay.py` の `_convert_alert()` が、受け取ったアラートを `SecurityEvent` に変換する
2. `ai_analysis.py` の `analyze_events()` が、分析に使う内容を組み立て、モデルの出力をスキーマで確かめる

## 1.2　実装を読む

> **実行先：VM 230**

⟦C1⟧

- Wazuh の7項目から `SecurityEvent` を作り、許可していない項目は `extra="forbid"` で拒む
- AI に渡す内容は、はっきり決めた6項目だけ
- イベントの要約は、AI に送る前と履歴に保存する前に伏せ字にする
- AI の提案は Pydantic で確かめ、証拠のイベントの ID が入力に含まれることも確かめる
- 一時的な遮断の提案には、グローバルの IP、TTL 1〜900秒、別々の証拠2件が要る

# 第2章　API・保存・公開の範囲

## 2.1　API から分析・保存へ

> **実行先：VM 230**

⟦C2⟧

| API | 処理 |
|---|---|
| `/api/v1/wazuh/events` | Wazuh のイベントを取るだけ |
| `/api/v1/wazuh/analyze` | 取ったイベントを AI の分析に渡す |
| `/api/v1/analysis` | 受け取ったイベントを直接 AI で分析する |

DB の初期化はアプリケーションの起動のときに行われます。`save_analysis()` は、分析の結果・証拠・操作の提案・承認の記録・監査のログを保存します。

## 2.2　ルートと、操作の実行の境目

> **実行先：VM 230**

⟦C3⟧

2つの分析の API は、どちらも `save_analysis()` を呼んでいました。一方、次の2つがわかりました。

1. **API の認証**：FastAPI のルートに、認証の依存関係やミドルウェアは無い
2. **操作の実行**：承認の状態を DB に記録するところまでで、Action Gateway・承認の API・ファイアウォールの操作は無い

## 2.3　外への公開と DB の権限

> **実行先：VM 230**

⟦C4⟧

| 項目 | 結果 |
|---|---|
| API の待ち受け | `127.0.0.1:8000` だけ（LAN には出ていない） |
| 実行のユーザー | 専用の `ai-defense` |
| SQLite の DB | `ai-defense:ai-defense`・`600` |
| DB のディレクトリ | `750` |

API に認証が無いことは残ります。localhost だけでも同じ VM のほかのプロセスからはアクセスできるので、ほかと連携する前に認証を考える必要があります（第56部〜で行います）。

## 2.4　承認の状態と保存

> **実行先：VM 230**

⟦C5⟧

分析の結果の保存はトランザクションの中で行われ、操作を実行する API やファイアウォールの操作はコードにありませんでした。

# 第3章　systemd による隔離

> **実行先：VM 230**

⟦C6⟧

| 設定 | 状態 |
|---|---|
| `ProtectSystem=strict`・`ProtectHome=yes` | あり |
| 書き込める場所 | DB の `/opt/ai-defense-manager/data` だけ |
| Linux の capabilities | 空 |
| `NoNewPrivileges=yes` | あり |
| `PrivateTmp`・`PrivateDevices`・`ProtectProc=invisible` | あり |
| メモリ・タスクの上限 | 1GiB・64 |
| `RestrictAddressFamilies` | `AF_INET`（IPv4 だけ） |

AI Defense Manager に root の権限やネットワークの管理の capability は付いていません。`AF_INET` だけなので IPv6 のソケットは使えませんが、いまの Relay・Ollama への接続は IPv4 です。

# 第4章　伏せ字の処理を試す

## 4.1　入力と出力の安全の点検

> **実行先：VM 230**

⟦C7⟧

イベントの入力の側は次のとおりでした。

- イベントの要約は LLM に送る前に伏せ字にする（Bearer のトークン・よくある秘密の情報・メールアドレス・IP アドレス）
- LLM に渡す内容は、許可リストで組み立てる
- Wazuh のイベントの IP・エージェントの名前は LLM に送らない
- LLM の答えは JSON Schema と Pydantic で確かめる

一方、LLM の出力の側に対策が要ることがわかりました（第5章）。

## 4.2　モデルと設定

> **実行先：VM 230**

⟦C8⟧

モデルの名前は `ai_analysis.py` に `qwen3:8b` と書かれていて、`config.py` に設定の項目はありませんでした。Ollama の接続先は `192.168.0.180:11434` です。ここは変えません。

## 4.3　合成したデータで試す（14件）

本番のコードは変えず、合成したデータで、秘密の情報・メール・IPv4/IPv6 のマスク、制御文字、512文字の上限、ふつうの文章が残ることを試します。

> **実行先：VM 230**

⟦C9⟧

14件すべて合格でした。

## 4.4　元の値が残らないか（10件）

> **実行先：VM 230**

⟦C10⟧

10件すべて合格で、伏せ字の印が出て、元の秘密の情報が残らないことを確かめました。わかっている形にしか効かないので、知らない形の秘密の情報まで消せるとは限りません。

# 第5章　LLM の出力の点検

## 5.1　保存の直前の処理

> **実行先：VM 230**

⟦C11⟧

問題が2つ見つかりました。

1. **LLM の出力をそのまま保存する**：`proposal.summary` と `proposal.reasoning` は、秘密の情報が入っていても伏せ字にされずに SQLite に保存される
2. **承認が要るかどうかを LLM が決められる**：IP の遮断のほかの提案では `requires_human_approval=false` が通り、保存の処理もその値を使う

いまは Action Gateway も実行の機能も無いので、これがすぐにファイアウォールの操作につながることはありません。

## 5.2　API の返す値と承認

> **実行先：VM 230**

⟦C12⟧

⟦C13⟧

ルーターの実体は `app/api/analysis.py` と `app/api/wazuh.py` でした。

## 5.3　ハンドラーの本体

> **実行先：VM 230**

⟦C14⟧

- `/api/v1/analysis`：LLM の提案を保存したあと、そのまま返す
- `/api/v1/wazuh/analyze`：Wazuh のイベントを取り、LLM で分析し、保存したあと、同じ提案を返す
- どちらも `response_model=AIAnalysisProposal` だが、このスキーマは長さや型を確かめるだけで、秘密の情報は除かない

そこで、保存の直前だけでなく、**LLM の答えを受け取った直後に、提案を伏せ字にする**必要があります。

## 5.4　直し方を決めるための点検

> **実行先：VM 230**

⟦C15⟧

| 問題 | 内容 |
|---|---|
| LLM の出力の伏せ字 | `summary` は最大2,000文字、`reasoning` は最大4,000文字で、伏せ字にせずに保存・返却している。いまの伏せ字の処理はイベントの入力用で、512文字に切るため、そのままは使えない |
| 承認が要るかどうか | LLM が `requires_human_approval=false` を返せる |

LLM は分析の担当に限り、出力の安全と承認の判断は AI Defense Manager の側で保証する、という方針で、次の第54部で直します。

# おわりに

第53部で、VM 230 の中の分析から保存までの流れを点検しました。

| 項目 | 結果 |
|---|---|
| 入力 | 7項目に絞り、知らない項目は拒む。要約は伏せ字にする。AI に送るのは6項目 |
| 公開 | `127.0.0.1:8000` だけ。DB は `600` |
| 隔離 | systemd で書き込める場所・capabilities・メモリなどを制限 |
| 伏せ字の試験 | 14件・10件すべて合格 |
| 見つかった問題 | LLM の出力を伏せ字にせずに保存・返却している。承認が要るかどうかを LLM が決められる。API に認証が無い |
| 操作の実行 | 機能が無い（提案の保存まで） |

次の第54部では、LLM の出力の伏せ字と、承認の方針を直します。
