# はじめに

## 本書について

本書は「AI自律型サイバー防御システム 構築マニュアル」前編の第18部です。AI の分析の結果と、その根拠になったイベント、防御の提案と承認の状態を、VM 230 の中の SQLite に記録します。

PostgreSQL のサーバーは、当面は使いません（構築時に「当面は VM 230 内の SQLite で保存する」方針にしました）。SQLite なら Python の標準のライブラリ（`sqlite3`）だけで作れ、パッケージを足す必要がありません。

| 項目 | 設計 |
|---|---|
| DB | SQLite 3 |
| 保存先 | `/opt/ai-defense-manager/data/ai-defense.db` |
| ジャーナル | WAL |
| DBへのアクセス | Python 標準の `sqlite3` |
| 実行ユーザー | `ai-defense` |
| トランザクション | 分析の結果と証拠のイベントをまとめて保存する |
| 同じ分析 | 分析するたびに別の記録にする |
| 承認 | 初めの状態は `pending` |
| 防御の実行 | 今回は作らない |

テーブルは次の5つです。

| テーブル | 中身 |
|---|---|
| `analysis_runs` | AI の分析の実行の記録 |
| `analysis_evidence` | 分析の対象にしたイベントの識別子・要約 |
| `action_proposals` | AI が提案した防御の内容 |
| `action_approvals` | 人による承認・却下の状態 |
| `audit_logs` | 操作の記録（監査ログ） |

Wazuh の生のログ（`full_log`）、任意の `data`、コマンド、ユーザー名、認証の情報は保存しません。

# 第3章　APIに組み込む

## 3.1　request_idも保存する

⟦C18⟧

`AIAnalysisRequest` には `request_id` があるので、同じリクエストの再送を見分けるために保存します。また、SQLite への書き込みは `asyncio.to_thread()` で行い、FastAPI の処理を長く止めないようにします。

API への組み込み方は次のとおりです。

- 分析が成功した後に保存する
- 保存に失敗したら `503` を返す（保存できなかった分析の結果を、成功として返さない）
- アプリの起動のとき（`lifespan`）に DB を初期化する

# おわりに

第18部で、AI の分析の結果を SQLite に残すようにしました。

| 項目 | 状態 |
|---|---|
| DB | `/opt/ai-defense-manager/data/ai-defense.db`（`ai-defense` の `600`、WAL） |
| テーブル | 5つ（分析・証拠・提案・承認・監査） |
| systemd | `ProtectSystem=strict` のまま、`data` だけ書き込みを許可 |
| 保存 | 分析が成功した後に保存。失敗したら `503` |

次の部では、SQLite に保存する内容と、LLM に送る内容を見直し、余計な情報を出さないようにします。
