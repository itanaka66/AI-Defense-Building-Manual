# はじめに

## 本書について

本書は「AI自律型サイバー防御システム 構築マニュアル」第4巻の第56部です。第55部までで、VM 230 の AI Defense Manager の入力・出力・大量の要求への備えを整えました。残っていた大きな課題は、**API に認証が無い**ことです。ここでは、認証を作る前に、読み取りだけで次のことを点検し、設計を決めます。

1. API の認証・認可と、API に届く経路
2. ローカルのアカウントの権限と、認証の情報・DB の保護
3. ネットワークの境目（ファイアウォール・IPv6・SSH）
4. 認証を組み込む場所と、トークンの方式

構築の途中で、次のことを決めました。

- API は、将来は**別の VM の Web UI や管理の端末からも使う**前提で設計する
- Web UI の VM はまだ決めていないので、接続元の IP の制限は、決まってから行う

## 本書の表記

- コマンドやプログラムは、構築時に実際に使用したものをそのまま掲載しています。改変していません。
- 実行先は、各手順の「実行先」に示します。
  - **VM 230**：ai-defense-manager（root）

# 第1章　API の認証と届く経路

## 1.1　認証・認可

> **実行先：VM 230**

⟦C0⟧

| 項目 | いま | 判定 |
|---|---|---|
| API の認証 | 無い | 対応が要る |
| API の認可 | 無い | 対応が要る |
| OpenAPI の Security | 定義が無い | 対応が要る |
| 待ち受け | `127.0.0.1` だけ | よい |
| `/health` | 認証なし | 内部だけなら許す |
| 本文の大きさの制限 | 256KiB | 対応済み |
| 分析の同時の実行の制限 | 1 | 対応済み |

分析の API は、ローカルのプロセスから認証なしで Ollama の推論と SQLite への書き込みを頼めます。

## 1.2　API に届く経路

> **実行先：VM 230**

⟦C1⟧

VM 230 に Nginx・Apache・Caddy・Cloudflared は動いておらず、API を呼ぶ既存のクライアントも見つかりませんでした。SSH は IPv4・IPv6 のすべてのインターフェースで待ち受けています。いまの主な脅威は、外からの直接のアクセスより、**VM 230 の中のローカルのアカウントやプロセスによる不正な利用**です。

# 第2章　アカウント・認証の情報・DB

## 2.1　ローカルのアカウントの権限

パスワードや SSH の秘密の鍵は表示しません。

> **実行先：VM 230**

⟦C2⟧

| アカウント | 権限 |
|---|---|
| `aidefense`（ログインに使う） | `sudo`（root になれる）・`lxd`・`adm` |
| `ai-defense`（サービス用） | `/usr/sbin/nologin`、専用のグループだけ |

`aidefense` は実際には管理者なので、API に認証を足しても、このアカウントが root になることまでは防げません。認証の目的は、一般のユーザーや権限の限られたローカルのプロセスからの不正な呼び出しを防ぐことです。`sudo`・`lxd` は運用に要る可能性があるので変えません。

## 2.2　認証の情報の保護

> **実行先：VM 230**

⟦C3⟧

| 対象 | 状態 |
|---|---|
| `/etc/ai-defense-manager/credentials` | `root:ai-defense`・`750` |
| Relay のトークン・CA の証明書 | `640` |
| `ai-defense` の読み取り | できる |
| `aidefense` の読み取り（ふつうの権限） | できない |
| アプリケーションの Python のソース | `root:ai-defense`・`640` |

## 2.3　認証の情報の渡し方と DB

> **実行先：VM 230**

⟦C4⟧

- systemd の `LoadCredential` は使っておらず、動いているプロセスに `CREDENTIALS_DIRECTORY` もない
- Relay の認証の情報は `/etc/ai-defense-manager/credentials/` から直接読み、ファイルの権限で守っている
- `aidefense` は、Relay の認証の情報のディレクトリにも、DB のファイル・ディレクトリにも、直接はアクセスできない

API の認証のトークンは、Relay のトークンとは別に管理します。

# 第3章　ネットワークの境目

## 3.1　インターフェースと待ち受け

> **実行先：VM 230**

⟦C5⟧

VM 230 は `192.168.0.221/24` で、API は `127.0.0.1:8000` だけで待ち受けています。ほかの VM から 8000 番に直接はつながりません。API を `0.0.0.0:8000` にいきなり変えることはしません。

## 3.2　ファイアウォールと IPv6

> **実行先：VM 230**

⟦C6⟧

| 項目 | 結果 | 評価 |
|---|---|---|
| API の待ち受け | `127.0.0.1:8000` | よい |
| IPv4 の iptables | ルールなし | 対策が要る |
| IPv6 の ip6tables | ルールなし | 対策が要る |
| nftables | iptables 互換、実際のルールなし | — |
| UFW | 有効だが `inactive` と表示 | 調べる |
| IPv4・IPv6 の転送 | 0（無効） | よい |
| IPv6 のアドレス | グローバル | 注意 |

VM 230 の中に、受信をふるい分ける設定は確かめられませんでした。Proxmox や上のルーターのファイアウォールまで無効とは言えませんが、この点は残っている課題にします（運用マニュアルの第6章）。

## 3.3　SSH

> **実行先：VM 230**

⟦C7⟧

`PermitRootLogin no`・`PasswordAuthentication no`（`00-local-hardening.conf`）・`PubkeyAuthentication yes`・`KbdInteractiveAuthentication no` でした。

> **実行先：VM 230**

⟦C8⟧

VM 230 では `ssh.service` が常に動くのではなく、`ssh.socket` がポート 22 を持ち、接続が来たときに `ssh.service` を起動する作りでした（IPv4 `0.0.0.0:22`、IPv6 `[::]:22`）。`ssh.service` が `inactive` でも、SSH が止まっているわけではありません。

> **実行先：VM 230**

⟦C9⟧

`/run/sshd` は、`ssh.service` が起動するときに systemd が作ります（`RuntimeDirectory`）。設定のファイルは `00-local-hardening.conf`、`50-cloud-init.conf` の順に読まれ、OpenSSH は最初に設定された値を使うので、`PasswordAuthentication no` が優先されます。SSH の設定は変えません。

# 第4章　認証の設計

## 4.1　組み込む場所

> **実行先：VM 230**

⟦C10⟧

- API のルーターは2つ（`/api/v1`：AI の分析、`/api/v1/wazuh`：Wazuh のイベントの取得・分析）
- 認証のミドルウェア・`Depends`・`HTTPBearer` などはまだ無い
- `/health` はルーターの外にあり、認証から切り離せる
- 本文の大きさの制限のミドルウェアは残せる
- `tests/` のディレクトリは無い

## 4.2　決めた設計

> **実行先：VM 230**

⟦C11⟧

| 対象 | いま | 方針 |
|---|---|---|
| AI の分析の API | 認証なし | 認証が要る（`analyze`） |
| Wazuh のイベントの取得 | 認証なし | 認証が要る（`read`） |
| Wazuh の分析 | 認証なし | 認証が要る（`analyze`） |
| `/health` | 認証なし | そのまま |
| `/docs`・`/redoc`・`/openapi.json` | 認証なし | 本番では無効にする |
| クライアントごとの失効 | 無い | 作る |
| 権限の分離 | 無い | 作る（`read`・`analyze`） |

トークンの方式は次のとおりです。

- 推測できない乱数の Bearer のトークンを、クライアントごとに発行する
- SQLite には、トークンそのものではなく SHA-256 のハッシュだけを保存する
- 比べるときは `hmac.compare_digest` を使う
- 有効期限・失効を持たせる
- Relay のトークンとは完全に分ける
- LLM に認証の情報や実行の権限を渡さない
- API は `127.0.0.1:8000` のままにし、ほかの VM から使うときは、TLS のついた入口を別に用意する

# おわりに

第56部で、API の認証を作る前の点検をし、設計を決めました。

| 項目 | 結果 |
|---|---|
| API | 認証・認可が無い。`127.0.0.1:8000` だけ |
| アカウント | `aidefense` は管理者、`ai-defense` はサービス専用（権限は分かれている） |
| 認証の情報 | ファイルの権限で守っている（`root:ai-defense`・`640`） |
| ネットワーク | VM 230 の中にファイアウォールのルールは無い（課題）。SSH はソケットで起動、パスワードの認証は無効 |
| 認証の設計 | クライアントごとの Bearer のトークン（`read`・`analyze`）、ハッシュで保存、失効・期限あり、ドキュメントの API は無効 |
