# はじめに

## 本書について

本書は「AI自律型サイバー防御システム 構築マニュアル」第4巻の第67部です。第66部で、VM 230 の FSS の検証を自動にしましたが、その結果を Wazuh に知らせる経路はありませんでした。ここでは、連携の前に VM 220 の Wazuh Manager の側を読み取りだけで調べます。

1. Wazuh Manager がエージェントを受け入れる構成かを確かめる
2. Relay（8765）の役割を調べる（読むだけの API で、イベントを入れる口ではない）
3. ローカルのルール `local_rules.xml` が XML として壊れていることを見つけ、作りを調べる
4. 本番のファイルには触れずに、直した候補のファイルを作る

設定の変更・エージェントの登録・通信の試験・サービスの再起動はしません。認証の情報や秘密の鍵も表示しません。

## 本書の表記

- コマンドやプログラムは、構築時に実際に使用したものをそのまま掲載しています。改変していません。
- 実行先は、各手順の「実行先」に示します。
  - **VM 220**：security-core（root）

## 2.2　どこで壊れているか

> **実行先：VM 220**

⟦C4⟧

- ほかの複数の控えも同じ21行目で失敗する

Wazuh の資料では、ルールのファイルのグループは1つの `<group>` で囲み、ルールごとの分類は各ルールの中の `<group>` で付けます。いまの分類（SSH と PostgreSQL）を保つため、次の形にします。

⟦C8⟧

また、ルール 100106 には次の要素がありました。

⟦C9⟧

`<same_source_ip />` は古い名前ですが、いまの Wazuh でも `<same_srcip />` の別名として動きます。変える必要はありませんが、新しい `<same_srcip />` にそろえ、検知の条件は変えません。

> **参考：** 構築の記録では、最初の修復のスクリプトが、想定と違うグループの作りを見つけて `ABORT: unexpected group structure` で止まりました。本番のファイルの SHA256・更新の日時・大きさは変わっていないことを確かめています。

## 3.2　候補のファイルを作る

本番のファイルは変えず、`/tmp` に候補を作り、XML の構文・8つのルールの ID・グループの分類・`same_srcip` を確かめます。

> **実行先：VM 220**

⟦C10⟧

| 確かめたこと | 結果 |
|---|---|
| XML の構文 | 正しい |
| ルールの数 | 8件（ID はすべて同じ） |

XML として正しいことと、Wazuh がルールとして受け入れることは別です。次の第68部で、本番に置かずに Wazuh で確かめます。
