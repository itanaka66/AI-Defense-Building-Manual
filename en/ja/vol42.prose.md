# はじめに

## 本書について

本書は「AI自律型サイバー防御システム 構築マニュアル」第3巻の第42部です。第41部までで、PostgreSQL の論理バックアップ（毎日 02:00）と LXC 109 の Proxmox のバックアップ（毎日 03:00）が TrueNAS の NFS に保存されるようになり、復元の試験にも合格しました。ここでは、保存したバックアップそのものを守ります。

1. バックアップのファイルを、root 以外のユーザーが読めないかを点検し、LXC のバックアップのディレクトリを root だけにする
2. 定期のバックアップのタイマーとジョブの状態を確かめる
3. TrueNAS のコンソールを使わず、**Proxmox から TrueNAS の API** でデータセットとスナップショットを調べる
4. TrueNAS の `backup` データセットに、日次・週次・月次の ZFS のスナップショットのタスクを作る

PostgreSQL の `globals.sql` にはロールのパスワードのハッシュが入ることがあり、LXC のアーカイブにはコンテナの中の設定や認証の情報が入ることがあります。そのため、読める人を root に限ります。

## 本書の表記

- コマンドやプログラムは、構築時に実際に使用したものをそのまま掲載しています。改変していません。
- 実行先は、各手順の「実行先」に示します。
  - **pve**：Proxmox のホスト（root）
- TrueNAS の API のコマンドは `--user root` で、実行のたびに TrueNAS の root のパスワードを聞かれます。パスワードは端末に入力し、画面には表示されません。コマンドの中やチャット・メモには書かないでください。

# 第1章　バックアップの読み取りの権限を点検する

## 1.1　いまの権限

> **実行先：pve**

⟦C0⟧

PostgreSQL のバックアップは、ディレクトリがすべて `0700`、ファイル（`.dump`・`globals.sql`・`SHA256SUMS` など）がすべて `0600`、所有者は `root:root` でした。こちらは変える必要はありません。

一方、LXC 109 のアーカイブは `0644` でした。

## 1.2　LXC のバックアップのディレクトリ

> **実行先：pve**

⟦C1⟧

| 対象 | 権限 | 評価 |
|---|---|---|
| `/mnt/pve/backup/dump/` | `0755` | 直す |
| LXC 109 のアーカイブ | `0644` | 直す |
| LXC 109 のログ | `0644` | 直す |
| PostgreSQL のバックアップ | `0700`・`0600` | よい |

`dump/` が `0755` で、アーカイブが `0644` なので、同じホストの一般のユーザーでもバックアップを読めます。

## 1.3　`dump/` を root だけにする

`dump/` ディレクトリだけを `0700` にします。所有者 `root:root`、TrueNAS の側の所有権・ACL、`/etc/vzdump.conf`、バックアップのジョブは変えません。root で動く Proxmox のバックアップ・復元・世代の管理はそのまま使えます。

> **実行先：pve**

## 1.4　変えたあとを確かめる

> **実行先：pve**

⟦C3⟧

`dump/` は `0700 root:root` になり、NFS の上にも反映されていました。アーカイブのファイル自体は `0644` のままですが、親のディレクトリが `0700` なので、root 以外はふつうのパスでは届きません。PostgreSQL のバックアップは `0700`・`0600` のままです。

# 第2章　Proxmox から TrueNAS の API を使う

TrueNAS（VM 100、`192.168.0.254`）の中の ZFS の情報は、Proxmox の `zfs list` では見えません。TrueNAS のコンソールで操作する代わりに、Proxmox から操作します。TrueNAS の SSH は待ち受けていない（`Connection refused`）ので、SSH は有効にせず、HTTPS の管理 API を使います。

## 2.1　API に届くか

認証の情報は送らず、応答だけを確かめます。

> **実行先：pve**

⟦C5⟧

API v2.0 は `HTTP 401`（認証が必要）、v1.0 は `302` でした。ネットワークの問題ではなく、認証が要る状態です。

## 2.2　認証を確かめる

バージョンの情報を読むだけです。

> **実行先：pve**

⟦C6⟧

`"TrueNAS-12.0-U8.1"`・`HTTP_STATUS=200` でした。これで SSH を有効にしなくても、Proxmox から API で調べられます。

## 2.3　バックアップのデータセット

> **実行先：pve**

| 項目 | 結果 |
|---|---|

# 第3章　スナップショットのタスクを作る

## 3.1　作るときの項目

> **実行先：pve**

⟦C11⟧

| 項目 | 意味 |
|---|---|
| `dataset` | 対象のデータセット |
| `recursive` | 子のデータセットも対象にするか |
| `lifetime_value`・`lifetime_unit` | 残す期間 |
| `naming_schema` | スナップショットの名前の形（`%Y %m %d %H %M` が必要） |
| `schedule` | 分・時・日・月・曜日 |
| `enabled` | 有効・無効 |

## 3.2　データセットの階層

`recursive` を有効にすると、子のデータセットも対象になります。範囲を広げすぎないように、階層を確かめます。

> **実行先：pve**

⟦C12⟧

`backup` に子のデータセットは無く、一つのファイルシステムでした。そこで **`backup` だけ・`recursive=false`** にします。

## 3.3　決めたスケジュール

バックアップが 02:00（PostgreSQL）と 03:00（LXC 109）に動くので、そのあとに取ります。

| 種類 | 実行 | 残す期間 | 名前 |
|---|---|---|---|
| 日次 | 毎日 04:00 | 7日 | `daily-%Y-%m-%d_%H-%M` |
| 週次 | 毎週日曜 04:10 | 4週 | `weekly-%Y-%m-%d_%H-%M` |
| 月次 | 毎月1日 04:20 | 3か月 | `monthly-%Y-%m-%d_%H-%M` |

TrueNAS の残す期間と、Proxmox の側のバックアップの世代の管理は、それぞれ別に動きます。なお、同じプールの上のスナップショットは、ディスクの故障や TrueNAS 本体を失ったときの独立したバックアップにはなりません。

# おわりに

第42部で、バックアップを読める人を root に限り、TrueNAS の側でも世代を残すようにしました。

| 項目 | 結果 |
|---|---|
| PostgreSQL のバックアップ | `0700`・`0600`（変えていない） |
| LXC のバックアップ | `dump/` を `0700` にした |
| TrueNAS の操作 | Proxmox から HTTPS の API（SSH は無効のまま） |
| データセット `backup` | 暗号化なし・LZ4・NFSV4 の ACL・子のデータセットなし |
| スナップショットのタスク | 日次（ID 1）・週次（ID 3）・月次（ID 4） |
| まだのこと | 11月23日の定期の実行の結果を確かめる |

次の第43部では、11月23日の定期の実行を確かめます。そこで、LXC 109 のバックアップの失敗と、Proxmox の再起動のあとに NFS がマウントされない問題が見つかり、それぞれを直します。
