# はじめに

## 本書について

本書は「AI自律型サイバー防御システム 構築マニュアル」前編の第12部です。第11部で作った AI Defense Manager の土台に、ローカルのLLM（Ollama）を使ってセキュリティイベントを分析する処理（AI分析サービス）を加え、APIから呼び出せるようにします。最後に、AI Defense Manager が Wazuh からアラートを読み取る方法を決めるため、Wazuh の API と Indexer を読み取りだけで調べます（設定は変更しません）。

## 本書の表記

- コマンドやプログラムは、構築時に実際に使用したものをそのまま掲載しています。改変していません。
- 実行先は、特に断りがない場合 **VM 230 ai-defense-manager（root）** です。Ollamaの調査は **VM 101 ollama-gpu（192.168.0.180、root）** で行います。
- AIの出力の内容（要約・確からしさなど）は、実行するたびに変わります。

## 分析の流れ

1. セキュリティイベント（第11部の `SecurityEvent`）をまとめて、AI分析の依頼（`AIAnalysisRequest`）にする
2. Ollama の `/api/chat` に、指示（システムプロンプト）と依頼をJSONで送る
3. 返ってきたJSONを、AIの分析の結果（`AIAnalysisProposal`）として検証する。型や安全のための制約に合わないものは受け付けない
4. 根拠のイベントIDが、依頼したイベントの中にあるかも確かめる

AIは「提案」を返すだけで、遮断などの操作は行いません。

## 5.7　調査で決まった方針

- アラートは Wazuh Indexer から読み取る。Indexer はほかのホストに公開しない。
- Indexer の証明書は `127.0.0.1` 用のため、security-core の中に中継のサービスを置き、そこからループバック（127.0.0.1）で接続する方式が候補。
- AI Defense Manager 用のユーザーには、読み取りだけの権限を付ける（`manage_wazuh_index` のような書き込みを含むロールは使わない）。

## 分かったこと

- `gemma4:12b` は、決めた型どおりのJSONを返せなかった。
- `qwen3:8b` は、思考モードのままだと出力が考える過程に使われ、答えが空になる。`think: false` で止めると、すぐにJSONを返す。
- タイムアウトは、推論の遅さではなく、モデルの読み込みを待つ間に起きていた。

## 残っていること

- Uvicorn は手で起動したもので、systemd のサービスにはしていません。構築の後、`kill` で停止しています。もう一度使うときは、4.3の起動のコマンドで起動します。
- `app/api/analysis.py` は新しく作ったファイルのため、ほかのファイルと同じ所有者・権限（`root:ai-defense`、`640`）にはしていません。
- AIの提案をもとに実際に対処する部分（Action Gateway）は、まだ作っていません。
- Wazuh からアラートを読み取る仕組み（中継のサービス、読み取り専用のユーザーとロール）は、方針を決めた段階で、まだ作っていません。
- **【未対応】** `app/api/analysis.py` の所有者・権限は、ほかのファイル（`root:ai-defense`、`640`）にそろえていません。
