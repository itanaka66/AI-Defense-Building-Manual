# はじめに

## 本書について

本書は「AI自律型サイバー防御システム 構築マニュアル」第3巻の第41部です。第40部で、PostgreSQL の論理バックアップを毎日 02:00 に動くようにしました。ここでは、もう一つのバックアップである **LXC 109 全体の Proxmox のバックアップ**を仕上げ、実際に復元できるかを試します。

1. LXC 109 を TrueNAS の NFS（`truenas-backup`）に初めてバックアップし、アーカイブを確かめる
2. 毎日 03:00 のジョブ `lxc109-daily` を有効にする
3. バックアップのときに出た thin pool の警告を、読み取りだけで調べる
4. バックアップを別の番号の LXC（CTID 310）に、**ネットワークを切ったまま**復元する
5. 復元した PostgreSQL が起動し、17個のデータベース・拡張機能・ロールの権限が戻っていることを確かめる

本番の LXC 109 は止めず、変更もしません。

## 本書の表記

- コマンドやプログラムは、構築時に実際に使用したものをそのまま掲載しています。改変していません。
- 実行先は、各手順の「実行先」に示します。
  - **pve**：Proxmox のホスト（root）

# 第3章　thin pool を調べる

thin pool がいっぱいになると、複数の VM・LXC のディスクの読み書きに影響します。ここでは設定を変えず、いまの状態だけを読みます。

## 3.1　使っている量と自動拡張の設定

> **実行先：pve**

⟦C4⟧

thin pool `pve/data` のデータの使用率は **61.69%**、メタデータの使用率は **2.18%** で、すぐに容量が無くなる状態ではありません。自動拡張の設定は無く、VG `pve` の空きは 16GiB でした。

## 3.2　足せる容量があるか

> **実行先：pve**

⟦C5⟧

⟦C6⟧

NVMe の3番目のパーティションはディスクの最後まで使われていて、まだ割り当てていない領域はありません。ほかの物理ディスクも、それぞれ別の VG に割り当て済みでした。

794GiB の thin pool を 5% 拡張するだけでも約 39.7GiB が必要なので、空きが 16GiB しかない状態で自動拡張を設定するのはやめます。ほかの VG からディスクを流用したり、いまのストレージを縮めたりもしません。将来、PVE 用のディスクを大きくするときに改めて設定します（運用マニュアルの点検の項目にしています）。

# 第4章　CTID 310 に復元する

## 4.1　復元の前に確かめる

> **実行先：pve**

⟦C7⟧

| 確かめたこと | 結果 |
|---|---|
| CTID 310 | 使われていない |
| `local-lvm` | `active`、空きは約 304GiB |
| バックアップ | 473MiB |
| バックアップの中の設定 | Debian・2 CPU・4GiB・rootfs 50GiB、非特権 |
| 元の IP アドレス | `192.168.0.151` |

バックアップの中には元の IP アドレスが入っています。そのままネットワークにつなぐと、本番の LXC 109 と IP アドレスが重なります。そこで、ネットワークを切った状態・自動で起動しない状態で復元します。

## 4.2　復元する

> **実行先：pve**

⟦C8⟧

`RESTORE_EXIT=0` で、CTID 310 の rootfs（50GiB）が作られ、約 1.7GiB のデータが展開されました。コンテナは止まったままです。

ただし、復元したあとの設定には、`--net0` で指定した設定ではなく、**バックアップの中の設定（本番と同じ IP アドレス）が残っていました**（第37部と同じ動きです）。まだ起動していないので、IP アドレスは重なっていません。

## 4.3　ネットワークを切る

起動の前に、CTID 310 の `net0` をはっきり切った設定にします。

> **実行先：pve**

⟦C9⟧

| 項目 | 状態 |
|---|---|
| `link_down` | `1`（仮想の NIC を切る） |
| IP アドレス | `ip=manual`・`ip6=manual`（本番の IP アドレスは無い） |
| `onboot` | `0` |
| 状態 | `stopped` |

# 第5章　復元した PostgreSQL を確かめる

## 5.1　起動する

ネットワークを切ったまま、CTID 310 だけを起動します。

> **実行先：pve**

⟦C10⟧

起動は `START_EXIT=0` でした。起動した直後は、SQL の接続が `the database system is starting up` で断られます。

## 5.2　起動が終わるのを確かめる

> **実行先：pve**

⟦C11⟧

ログの最後に `database system is ready to accept connections` があり、`pg_isready` も `accepting connections` を返しました。ログの `automatic recovery in progress` は、バックアップの時点で終わっていなかった WAL を戻した動きで、そのあとにリカバリの完了と接続の受け付けの開始が記録されています。

`systemctl is-active postgresql` が `inactive` と出ることがありますが、Debian では親のサービス `postgresql.service` は `active (exited)` となる作りで、実際のクラスタのサービスは `postgresql@17-main.service` です。異常ではありません。

## 5.3　データベースと拡張機能

> **実行先：pve**

⟦C12⟧

- PostgreSQL 17.11 が起動し、17個すべてのデータベースに接続できた
- `easywrider`・`postgres`・`vector_db` の3つで `vector 0.8.7`
- ほかのデータベースは `plpgsql 1.0`
- データベースの大きさも、元の記録と合っている

## 5.4　ロールと権限

パスワードのハッシュは表示しません。

> **実行先：pve**

⟦C13⟧

`wazuh_collector` は `SUPERUSER`・`CREATEDB`・`CREATEROLE`・`REPLICATION`・`INHERIT` がすべて無効で、所属するロールもありませんでした。テーブルの権限は `security_workbench.incident.alert_events` の `INSERT` だけです。

`information_schema.role_table_grants` だけでは、PUBLIC を通した権限や列ごとの権限まではわからないので、実効の権限も確かめます。

> **実行先：pve**

⟦C14⟧

| 対象 | 結果 |
|---|---|
| `incident.alert_events` の INSERT | 許可 |
| SELECT・UPDATE・DELETE | 不許可 |
| TRUNCATE・REFERENCES・TRIGGER | 不許可 |
| `incident` スキーマの USAGE | 許可 |
| `incident` スキーマの CREATE | 不許可 |
| 列ごとの権限 | 決めた14列への INSERT だけ |

全部のテーブルを対象にした検査でも、`incident.alert_events` 以外に権限はありませんでした。復元した `wazuh_collector` は、意図どおり INSERT だけの構成です。

> **参考：** ロールの一覧には `SUPERUSER` を持つロール（`agent_user`・`aiagent` など）もありますが、`wazuh_collector` とは別の話なので、この試験では変えていません。

## 5.5　CTID 310 を止める

検証が終わったので、CTID 310 を止めます。削除はせず、復元の検証用に残します。

> **実行先：pve**

⟦C15⟧

CTID 310 は止まり、`link_down=1`・`onboot=0` のままです。本番の CTID 109 は `running` のままでした。
