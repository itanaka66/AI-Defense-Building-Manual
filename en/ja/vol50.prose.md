# はじめに

## 本書について

本書は「AI自律型サイバー防御システム 構築マニュアル」第4巻の第50部です。第49部までで、VM 220 の Relay と VM 230 の AI Defense Manager のコードを直し、Relay だけを再起動しました。ここでは次のことを行います。

1. VM 230 の `ai-defense-manager.service` を再起動し、新しいコードを読み込ませる
2. VM 230 のアドレスを、DHCP の `192.168.0.33` から、固定の `192.168.0.221` に変える（DHCP は使わない）
3. VM 220 の Relay に残っていた古いアドレス（接続を許すクライアント）を、新しいアドレスに直す

VM 220（`192.168.0.220`）と並びの番号にすると、管理しやすくなります。

## 本書の表記

- コマンドやプログラムは、構築時に実際に使用したものをそのまま掲載しています。改変していません。
- 実行先は、各手順の「実行先」に示します。
  - **VM 230**：ai-defense-manager（root）
  - **VM 230（コンソール）**：Proxmox の画面の VM 230 の Console から root でログインしたもの
  - **VM 220**：security-core（root）

# 第2章　VM 230 のアドレスを固定する

## 2.1　いまの設定

> **実行先：VM 230**

⟦C2⟧

VM 230 は DHCP で `192.168.0.33/24` を受け取っていました（NIC は `enp6s18`）。API は `127.0.0.1:8000` だけで待ち受けているので、アドレスを変えても API が外に出ることはありません。ただし、SSH は一時的に切れることがあります。

## 2.2　DNS と管理の方式

> **実行先：VM 230**

⟦C3⟧

VM 230 は **Netplan と systemd-networkd** で管理され、`/etc/netplan/50-cloud-init.yaml` が `dhcp4: true` でした。DNS は `192.168.0.1`・`2404:1a8:7f01:a::3`・`2404:1a8:7f01:b::3` です。IPv6 はルーターの広告（RA）による自動の設定のまま残し、IPv4 だけを固定にします。

## 2.3　設定の全体と、アドレスの重なり

> **実行先：VM 230**

⟦C4⟧

`arping` は入っていなかったので、ping と近隣のキャッシュで確かめます。

> **実行先：VM 230**

⟦C5⟧

`192.168.0.221` からは ping の応答が無く、近隣のキャッシュは `FAILED` でした。使われている様子はありません（ICMP に答えない機器や止まっている機器があり得るので、重なりが無いとまでは言えません）。

| 項目 | 変えたあと |
|---|---|
| IPv4 | `192.168.0.221/24`（固定） |
| ゲートウェイ | `192.168.0.1` |
| IPv4 の DHCP | 無効 |
| IPv6 | RA による自動の設定のまま |
| DNS | いまの3つのアドレスのまま |
| DNS の検索のドメイン | `iptvf.jp` のまま |

## 2.4　設定のファイルを作る

設定のファイルを控えてから書き換えます。この段階では**設定を適用せず、インターフェースも再起動しません**。

> **実行先：VM 230**

⟦C6⟧

元の設定の控え（SHA256 一致）、Netplan の構文の検査、`netplan generate`（終了コード `0`）は、すべて成功しました。

## 2.5　`netplan try` で適用する

アドレスが変わると SSH が切れるので、**Proxmox の画面の VM 230 の Console** で実行します。`netplan try` は適用したあとに確認を求め、確認しなければ元に戻ります。

> **実行先：VM 230（コンソール）**

⟦C7⟧

> **重要：** `netplan try` が確認を求めたら、アドレスが `.221` になって通信できることを確かめてから確定します。`.33` のままなら確定しません。

`netplan try` は正常に終わり、設定は確定されました。自動で元に戻ることはありませんでした。

## 2.6　適用したあとを確かめる

> **実行先：VM 230（コンソール）**

⟦C8⟧

| 確かめたこと | 結果 |
|---|---|
| IPv4 | `192.168.0.221/24`（有効期限 `forever`） |
| IPv4 の DHCP | 無効 |
| 既定の経路 | `192.168.0.1`、ゲートウェイへの ping は 3/3 成功 |
| IPv6 の RA | 正常 |
| DNS | 3つのアドレスで正常 |
| API の待ち受け | `127.0.0.1:8000` |
| `/health` | `HTTP 200` |
| systemd | `active` |

# 第3章　Relay の許可するアドレスを直す

## 3.1　古いアドレスが残っているところ

VM 220 の Relay は VM 230 から接続される側なので、VM 230 の古いアドレスが設定に残っていないかを調べます。

> **実行先：VM 220**

⟦C9⟧

`/opt/ai-defense-relay/relay.py` の16行目に、`ALLOWED_CLIENT = "192.168.0.33"` が残っていました。

## 3.2　どう使われているか

> **実行先：VM 220**

⟦C10⟧

Relay は次の2段でクライアントを確かめています。

1. 接続元の IP アドレスが `ALLOWED_CLIENT` と一致すること
2. `Authorization: Bearer ...` のトークンが一致すること

いまのままでは、VM 230 の新しいアドレスからの接続が断られます。変えるのは `relay.py` の1行だけで、API のトークン・Wazuh の設定・許可した項目・待ち受けのアドレスとポートは変えません。

## 3.3　1行を直して再起動する

控えを作り、変わったのが1行だけであること・Python の構文・ファイルの権限を確かめてから、Relay を再起動します。

> **実行先：VM 220**

⟦C11⟧

`ALLOWED_CLIENT = "192.168.0.221"` に変わり、控えの SHA256 は一致、構文の検査は合格、権限は `640` のまま、再起動は終了コード `0`、状態は `active` でした。

## 3.4　待ち受けを確かめる

再起動の直後の `ss` には 8765 の待ち受けがまだ出ていなかったので、少し待ってから確かめます。

> **実行先：VM 220**

⟦C12⟧

| 項目 | 結果 |
|---|---|
| Relay | `active (running)`、MainPID `17962` |
| 待ち受け | `192.168.0.220:8765` |
| 許可するクライアント | `192.168.0.221` |
