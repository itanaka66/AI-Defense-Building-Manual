# はじめに

## 本書について

本書は「AI自律型サイバー防御システム 構築マニュアル」第4巻の第62部です。第61部で、journal の容量の上限を設定しました。ここでは、ログを読める人の範囲を最後に点検したうえで、**ログが書き換えられたことを見つけるための仕組み**を用意します。

systemd の journal には **FSS（Forward Secure Sealing）** という仕組みがあります。

- 秘密の側の封印の鍵（Seal 鍵）は VM の中に置き、一定の時間ごと（ここでは15分）に journal を封印する。鍵は時間とともに先へ進み、前の時間の鍵は残らない
- 検証の鍵は VM の外に保管し、`journalctl --verify --verify-key=…` で、封印したあとに書き換えられていないかを確かめる

設定の `Seal=yes`（既定）だけでは FSS は動かず、`journalctl --setup-keys` で鍵を作る必要があります。

## 本書の表記

- コマンドやプログラムは、構築時に実際に使用したものをそのまま掲載しています。改変していません。
- 実行先は、各手順の「実行先」に示します。
  - **VM 230**：ai-defense-manager（root）

> **注意：** 検証の鍵の中身は、画面に出したり、貼り付けたりしないでください。

# 第1章　ログを読める人の最後の点検

## 1.1　syslog

> **実行先：VM 230**

⟦C0⟧

`/var/log/syslog`・`/var/log/auth.log`・切り替えたログは `syslog:adm`・`640` で、追加の ACL はなく、サービスのアカウント `ai-defense` にログを読む権限は付いていませんでした。

## 1.2　journal

> **実行先：VM 230**

⟦C1⟧

| 項目 | 結果 |
|---|---|
| `/var/log/journal`・`/run/log/journal` | `root:systemd-journal`・`2755` |
| journal のファイル | `root:systemd-journal`・`640` |
| `systemd-journal` のグループ | メンバーなし |
| `ai-defense` | journal を読むグループに入っていない |

権限の変更は要りません。

## 1.3　整合性と永続の保存

> **実行先：VM 230**

⟦C2⟧

容量の上限（512MB・空き2GB・ファイル64MB）、表示されたファイルの検査はすべて合格、immutable の属性なし、`/var/log` は ext4 で読み書きのマウントでした。

# 第2章　FSS に対応しているか

> **実行先：VM 230**

⟦C3⟧

| 項目 | 判定 |
|---|---|
| systemd の FSS への対応 | 対応している（systemd 255） |
| Seal の既定 | 有効 |
| Seal の明示の設定 | なし |
| FSS の鍵のファイル | 見つからない |
| journal のヘッダーの `Tag objects` | 0 |
| FSS が動いているか | 動いていない |

journal の整合性の検査が合格でも、FSS による改ざんの検出とは別のものです。次の順で進めます。

1. FSS の鍵を作る
2. 検証の鍵を VM 230 とは別の安全な場所に保管する（第63部）
3. 秘密の鍵の権限と場所を確かめる
4. 新しくできる journal が封印されることを確かめる（第64部）
5. `journalctl --verify --verify-key=...` で確かめる手順を作る

すでにある journal に、さかのぼって FSS の保護が付くわけではありません。

# 第3章　FSS の鍵を作る

## 3.1　鍵を作る

標準の15分の間隔で鍵を作ります。検証の鍵は、VM 230 の root 専用のファイルに一時的に保存し、画面には出しません。journald は再起動しません。

> **実行先：VM 230**

⟦C4⟧

| 確かめたこと | 結果 |
|---|---|
| 終了コード | `0` |
| 秘密の側の FSS のファイル | `/var/log/journal/…/fss`、`root:systemd-journal`・`600` |
| 検証の鍵のファイル | `/root/fss-verification-key-20261124.txt`、`root:root`・`600` |
| journald | 動いたまま、再起動なし |

## 3.2　鍵の形を確かめる

> **実行先：VM 230**

⟦C5⟧

このスクリプトの形の検査は「43文字の標準の Base64」を前提にしていて、systemd が実際に出す形と合わず、`FAIL` になりました。検査のしかたを変えて確かめ直します。

> **実行先：VM 230**

⟦C6⟧

32バイトに正しくデコードでき、検証の鍵の形は正常でした（ファイルは44バイト、ASCII だけ、最後に改行）。

# おわりに

第62部で、ログを読める人の範囲を確かめ、FSS の鍵を作りました。

| 項目 | 結果 |
|---|---|
| ログの権限 | syslog・journal とも、サービスのアカウントは読めない |
| FSS への対応 | systemd 255 で対応、`Seal` は既定で有効 |
| FSS の鍵 | 15分の間隔で作った。秘密の側は VM 230 の journal のディレクトリ（`600`）、検証の鍵は `/root/fss-verification-key-20261124.txt`（`600`） |
| まだのこと | 検証の鍵を VM の外に保管する、封印が始まることを確かめる |

検証の鍵の保管先は、**Proxmox のホスト `pve` の root 専用の場所**に決めました。次の第63部で、VM 230 から安全に移します。
