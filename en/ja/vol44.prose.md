# はじめに

## 本書について

本書は「AI自律型サイバー防御システム 構築マニュアル」第3巻の第44部で、第3巻の最後の部です。第43部で、再起動のあとの NFS のマウントと、LXC 109 のバックアップの失敗を直しました。ここでは、バックアップの仕組みが全体として正しく動いているかを確かめ、第41部で復元した CTID 310 のデータベースを、本番の CTID 109 と細かく比べます。

1. Proxmox がバックアップを正式なバックアップとして認識しているか、ジョブと起動の依存関係が残っているかを確かめる
2. 復元の試験の用の CTID 310 と thin pool の状態を確かめる
3. CTID 310 をネットワークを切ったまま起動し、PostgreSQL を確かめる
4. 17個のデータベースの、テーブル・ビュー・インデックス・制約・拡張機能・スキーマの定義を、CTID 109 と比べる

データの変更・設定の変更・サービスの再起動はしません。すべて読み取りだけです。

## 本書の表記

- コマンドやプログラムは、構築時に実際に使用したものをそのまま掲載しています。改変していません。
- 実行先は、各手順の「実行先」に示します。
  - **pve**：Proxmox のホスト（root）

# 第1章　バックアップの仕組みを確かめる

## 1.1　カタログ・ジョブ・起動の依存関係

> **実行先：pve**

⟦C0⟧

| 項目 | 結果 |
|---|---|
| バックアップのカタログ | LXC 109 の2世代（11月22日 20:28、11月23日 09:43）が登録されている |
| `lxc109-daily` | 毎日 03:00、snapshot、zstd、`truenas-backup`、日次7・週次4・月次3、`/var/tmp`、有効 |

アーカイブは NFS の上にあるだけでなく、Proxmox のバックアップのカタログにも登録されています。

## 1.2　復元の方法と、アーカイブの中の設定

> **実行先：pve**

⟦C1⟧

アーカイブに記録された設定は、いまの CT109 と同じでした（Debian・amd64、2 vCPU、メモリ 4GB、ルートのディスク 50GB、非特権、`nesting=1,keyctl=1`、`192.168.0.151/24`、`onboot=1`）。本番の CT109 を上書きせず、別の CTID で確かめます。

## 1.3　CTID 310 と thin pool

> **実行先：pve**

⟦C2⟧

| 項目 | 状態 |
|---|---|
| `pve/data` | 794.30GiB、データの使用率 61.90%、メタデータ 2.19% |
| VG のまだ割り当てていない領域 | 16GiB |
| CTID 310 | 止まっている。rootfs `local-lvm:vm-310-disk-0`（50GB、使用率 5.47%）、`link_down=1`、`onboot=0` |

CTID 310 は第41部で復元したものがそのまま残っていて、ネットワークも切れています。新しい復元先は作らず、これを使います。

# 第2章　CTID 310 を起動して確かめる

## 2.1　ネットワークを切ったまま起動する

> **実行先：pve**

⟦C3⟧

CTID 310 は `running`、本番の CTID 109 も `running`、CTID 310 は `link_down=1`・`onboot=0` のままです。

## 2.2　PostgreSQL の状態

> **実行先：pve**

⟦C4⟧

PostgreSQL 17 の `main` は `online`、`127.0.0.1:5432` で接続を受け付け、`eth0` は `DOWN`、経路は無しでした。PostgreSQL は `0.0.0.0:5432` と `[::]:5432` でも待ち受けていますが、仮想の NIC が切れているので外には届きません。検証の間はこの隔離を保ちます。

## 2.3　データベースの一覧

> **実行先：pve**

⟦C5⟧

PostgreSQL 17.11、クラスタ `17/main` は `online`、データベースは17個、`pg_is_in_recovery()` は `false` でした。`postgresql.service` が `active (exited)` なのは、Debian の管理用のサービスとしては正常です。

## 2.4　所有者・拡張機能・インデックス・ログ

> **実行先：pve**

⟦C6⟧

各データベースに所有者があり、`vector` は `easywrider`・`postgres`・`vector_db` で `0.8.7`、全部のデータベースで無効なインデックス（`indisvalid=false` または `indisready=false`）は0件でした。

ロールの一覧のコマンドでは、`!~` が Bash の履歴の展開として解釈され、システムのロールを除く条件が効いていませんでした。データの壊れではありません。直したコマンドで取り直し、`pg_amcheck` があるかも確かめます。

> **実行先：pve**

⟦C7⟧

| 項目 | 結果 |
|---|---|
| ロール | 18個を取得できた |
| CTID 310 の rootfs | 空き 45GB |
| `pg_amcheck` | 入っていない（ここでは入れない） |

## 2.5　ログのエラーを切り分ける

ログには、`alert_events_pkey` の重複のキーのエラー（Wazuh の Collector の重複した INSERT の記録）、`security_workbench` の診断の SQL のエラー、起動の途中の接続による `FATAL` がありました。

> **実行先：pve**

⟦C8⟧

時刻を並べると、これらはバックアップの前から本番で記録されていたものや、診断のクエリの失敗、起動の途中の接続によるもので、データベースの壊れを示すものではありませんでした。

# 第3章　本番と比べる

バックアップを取ったあとも CT109 は動いているので、データが完全に同じであることは求めません。構造が同じかを比べます。

## 3.1　データベースの名前と大きさ

> **実行先：pve**

⟦C9⟧

CT109 と CT310 の両方に17個のデータベースがあり、名前もすべて同じでした。大きさには数KB〜約1MB の差がありますが、バックアップのあとの本番の更新による差と考えられます。CT310 は `onboot: 0`・`link_down=1` のままです。

## 3.2　テーブルとビューの数

`information_schema.tables` は接続しているデータベースしか見ないので、データベースごとに接続して数えます。

> **実行先：pve**

⟦C10⟧

出力は `データベース名|テーブル数|ビュー数|マテリアライズドビュー数` です。**17個のデータベースすべてで、CT109 と CT310 の数が同じでした**（テーブル 合計266、ビュー 1、マテリアライズドビュー 0）。

| データベース | テーブル（CT109） | テーブル（CT310） |
|---|---|---|
| agent_db | 18 | 18 |
| agent_memory | 31（ビュー 1） | 31（ビュー 1） |
| aipmo | 23 | 23 |
| easywrider | 29 | 29 |
| movie | 22 | 22 |
| novel | 22 | 22 |
| orchivio | 55 | 55 |
| winfilemgr | 8 | 8 |
| writers | 12 | 12 |

ほかの8個のデータベースも同じです。

## 3.3　インデックス・制約・拡張機能

> **実行先：pve**

⟦C11⟧

インデックスは全部で534個（無効・未準備は0個）、主キー・外部キー・一意制約・CHECK 制約の数、拡張機能の名前とバージョン（`vector 0.8.7` が3つ、`plpgsql 1.0` が17個）が、すべて同じでした。

## 3.4　スキーマの定義

数だけでなく、テーブルの定義・列・データの型・インデックスや制約の定義まで比べます。`pg_dump --schema-only` の出力を SHA256 にします。データの本体は出力しません。

> **実行先：pve**

⟦C12⟧

17個のうち16個は、CT109 と CT310 の SHA256 が同じでした。違ったのは `novel` だけです。

## 3.5　`novel` の差

> **実行先：pve**

⟦C13⟧

CT109 にあって CT310 に無い列が2つありました（`ollama_api_key`・`controller_ollama_api_key`、`character varying(500)`）。列の値（API キー）には触れず、どのテーブルの列かを確かめます。

> **実行先：pve**

⟦C14⟧

| 列 | CT109 | CT310 |
|---|---|---|
| `translator_pool` | ある | ある |
| `ollama_api_key` | ある | 無い |
| `controller_ollama_api_key` | ある | 無い |

対象は `novel.public.runtime_config` テーブルです。この2列は、開発中のアプリケーションのスキーマの変更による差です（構築の記録では「開発中のもの」として扱いました）。障害やバックアップの壊れではないので、直す対象にしません。

# おわりに

第44部で、バックアップの仕組みを確かめ、復元したデータベースを本番と比べました。

| 確かめたこと | 結果 |
|---|---|
| バックアップのカタログ | LXC 109 の2世代が登録されている |
| ジョブ・起動の依存関係 | `tmpdir: /var/tmp`、TrueNAS を待つサービスが残っている |
| CTID 310 の隔離 | `link_down=1`・`onboot=0`、`eth0` は `DOWN` |
| PostgreSQL 17.11 | 起動し、17個のデータベースに接続できる |
| テーブル・ビューの数 | 17個すべて同じ |
| インデックス・制約・拡張機能 | すべて同じ。無効なインデックスは0 |
| スキーマの定義 | 16個が同じ。`novel` の差は開発中の変更 |

これで、第3巻で用意したバックアップの仕組みは次のようになりました。

| 時刻 | 処理 | 保存先 |
|---|---|---|
| 毎日 02:00 | PostgreSQL の論理バックアップ（17個の DB とグローバルオブジェクト） | TrueNAS の NFS `postgresql/`（日次7・週次4・月次3） |
| 毎日 03:00 | LXC 109 の Proxmox のバックアップ（一時ディレクトリは `/var/tmp`） | TrueNAS の NFS `dump/`（日次7・週次4・月次3） |
| 毎日 04:00・日曜 04:10・1日 04:20 | TrueNAS の ZFS のスナップショット | `backup` データセット（7日・4週・3か月） |
| 起動のとき | TrueNAS の VM 100 と NFSv3 の応答を待ってからマウント | `/mnt/pve/backup` |

CTID 310 は、ネットワークを切ったまま動いています。使い終わったら第41部の 5.5 の手順で止めてください。全部のテーブルのデータが同じかどうかや、アプリケーションからの接続までは確かめていません。

第3巻はここまでです。第4巻では、AI Defense Manager の LLM まわりの仕上げ（Wazuh のルールの修復、LLM に渡す入力の形、VM 230 の固定 IP、出力の検査、API トークンの認証、ログの改ざんの検知）と、AI 防御のエージェントの構築に進みます。
