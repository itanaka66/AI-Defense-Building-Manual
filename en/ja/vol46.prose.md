# はじめに

## 本書について

本書は「AI自律型サイバー防御システム 構築マニュアル」第4巻の第46部です。第45部で、Wazuh の設定ファイルを修復しました。ここでは、LLM に渡すデータを決めるために、Wazuh のアラートの中身を、**値を表示せずに**数と種類だけで調べます。

1. アラートの数・重大度・ルール・分類のグループを集計する
2. 多いルールの定義を確かめ、Wazuh 自身の検査（`wazuh-analysisd -t`）を行う
3. アラートの JSON にある項目の名前を調べ、LLM に渡してよい項目と、渡してはいけない項目を分ける
4. 渡してよい7項目の型と制約を決め、実際のアラートでメモリの上だけで変換を試す

イベントの本文・IP アドレス・ユーザー名・コマンドは表示しません。ファイルへの書き込み、DB への登録、LLM への送信もしません。

## 本書の表記

- コマンドやプログラムは、構築時に実際に使用したものをそのまま掲載しています。改変していません。
- 実行先は、各手順の「実行先」に示します。
  - **VM 220**：security-core（root）
  - **pve**：Proxmox のホスト（root）

# 第1章　アラートを集計する

## 1.1　数と重大度

> **実行先：VM 220**

⟦C0⟧

いまの `alerts.json` には、正しく読めるアラートが **245件** ありました（重大度 Level 3 が228件、Level 7 が17件、読めないものは0件）。これはファイルに残っている件数で、すべてが最近起きたとは限りません。

## 1.2　ルールと分類のグループ

> **実行先：VM 220**

⟦C1⟧

- 245件のうち220件に `pam` のグループが付いている（グループは重ねて数える）
- ルール `5501` と `5502` で合わせて220件
- Level 7 の17件はすべてルール `100103`（グループ `local`・`error`）
- ルール `87203` が6件（グループ `proxmox-ve`）

ルールの ID やグループの名前だけでは、攻撃かどうかはわかりません。

# 第2章　ルールの定義を確かめる

## 2.1　ルールの説明と分類の条件

イベントの本文は読まず、ルールの定義の説明と分類の条件だけを取り出します。

> **実行先：VM 220**

⟦C2⟧

| ルール | 意味 |
|---|---|
| `5501` | PAM のログインのセッションの開始 |
| `5502` | PAM のログインのセッションの終了 |
| `5715` | SSH の認証の成功 |
| `87203` | Proxmox VE の認証の成功 |

## 2.2　ルールのファイルの場所

> **実行先：VM 220**

⟦C3⟧

`100103` は `/var/ossec/etc/rules/local_rules.xml`、`5402` は標準のルールのファイル `0020-syslog_rules.xml` にありました。

Python の標準の XML のパーサーでは27個のルールのファイルが `ParseError` になりますが、Wazuh のルールのファイルは1つのファイルに最上位の要素を複数置く形なので、これだけでは壊れているとは言えません。Wazuh 自身の検査で確かめます。

## 2.3　Wazuh 自身の検査

> **実行先：VM 220**

⟦C4⟧

`wazuh-analysisd -t` は終了コード `0` でした。Wazuh はルールの設定を正しく読めています。

## 2.4　ローカルのルールの定義

> **実行先：VM 220**

⟦C5⟧

| ルール | 件数 | 意味 | 評価 |
|---|---:|---|---|
| 5501 | 112 | PAM のログインのセッションの開始 | ふつうの認証の記録 |
| 5502 | 108 | PAM のログインのセッションの終了 | ふつうの認証の記録 |
| 100103 | 17 | PostgreSQL の ERROR のイベント | 調べる対象 |
| 87203 | 6 | Proxmox VE の認証の成功 | ふつうの認証の記録 |
| 5715 | 1 | SSH の認証の成功 | ふつうの認証の記録 |
| 5402 | 1 | sudo で root の権限を取った | 操作が正しいかを確かめる対象 |

`100100` は Level 0 の「PostgreSQL sanitized JSON event base rule」、`100103` は Level 7 の「PostgreSQL ERROR event detected」です。17件は、CT 109 の伏せ字にした PostgreSQL のイベントを Wazuh が検出したもので、攻撃ではなく、アプリケーションやデータベースのエラーとして扱います。

# 第3章　LLM に渡す項目を決める

## 3.1　アラートの JSON の項目の名前

値は表示せず、項目の名前だけを数えます。

> **実行先：VM 220**

⟦C6⟧

245件すべてに `full_log` と `data` がありました。`agent.ip`・`agent.name`・`data.dstuser`・`data.srcuser`・`data.command`・`data.pwd` など、LLM にそのまま渡してはいけない情報も入っています。そこで、**アラートの JSON をそのまま LLM に送る方式は使いません**。

| 項目 | 扱い |
|---|---|
| `timestamp` | 渡す（形を確かめてから） |
| `rule.id` | 渡す |
| `rule.level` | 渡す |
| `rule.groups` | 渡す（許可リストで制限） |
| `rule.description` | 渡す（長さと文字を確かめる） |
| `decoder.name` | 渡す（許可リストで制限） |
| `agent.id` | 渡す |
| `agent.ip`・`agent.name` | 除く |
| `full_log` | 必ず除く |
| `data` | まるごと除く |
| `predecoder`・`manager`・`location`・`id` | 原則として除く |

## 3.2　7項目の型と欠け

> **実行先：VM 220**

⟦C7⟧

245件すべてで、7項目が欠けずに、考えた型で入っていました。

## 3.3　7項目の制約

> **実行先：VM 220**

⟦C8⟧

7項目すべてで、245件のうち245件が制約を満たし、合わない値は0件でした。これで、LLM の入力の許可リスト（v1）を決めます。

| 項目 | 型 | 制約 |
|---|---|---|
| `timestamp` | 文字列 | ISO 8601 の日時 |
| `rule_id` | 文字列 | 数字1〜16桁 |
| `severity` | 整数 | 0〜16 |
| `groups` | 文字列の配列 | 英数字と `_.-`、それぞれ64文字まで |
| `description` | 文字列 | 160文字まで |
| `decoder` | 文字列 | 英数字と `_.-`、64文字まで |
| `agent_id` | 文字列 | 数字1〜16桁 |

大事なのは、**許可した項目のほかは写さない**ことです。`data` や `full_log` を除くだけでなく、知らない項目はすべて捨てます。

## 3.4　変換をメモリの上で試す

実際の245件を、メモリの上だけで変換します。

> **実行先：VM 220**

⟦C9⟧

| 確かめたこと | 結果 |
|---|---|
| 変換できた件数 | 245件すべて |
| 変換のエラー・キーの構成のエラー | 0件 |
| 禁止した項目の混入 | 0件 |
| JSON の読み直しのエラー | 0件 |
| 変換したあとの合計の大きさ | 46,848 バイト |
| 1件の最大の大きさ | 225 バイト |

LLM に渡すイベントを、小さく決まった形にできることを確かめました。ただし、これはいまの245件での確認で、実際に組み込むときは入力を毎回確かめます。

# 第4章　データの経路

新しいサービスは作らず、いまの環境を使います。考えたデータの経路は次のとおりです。

⟦C10⟧

CT 109 の PostgreSQL のフィルターは、PostgreSQL のイベントを伏せ字にする境目として、いまの役割のままにします。Wazuh のアラートの変換と混ぜたり、フィルターを変えたりはしません。

最後に、関係する3台の VM の配置を確かめます。

> **実行先：pve**

⟦C11⟧

| VM | 役割 | 状態 | vCPU | メモリ | 接続 |
|---|---|---|---:|---:|---|
| 220 | Wazuh（security-core） | 動いている | 8 | 16GB | vmbr0・vmbr1 |
| 230 | AI Defense Manager | 動いている | 4 | 8GB | vmbr0 |
| 101 | Ollama（GPU） | 動いている | 16 | 128GB | vmbr0 |

> **注意：** `qm` は Proxmox のホストのコマンドです。VM 220 の中で実行すると `qm: command not found` になります。プロンプトが `root@pve:~#` になっていることを確かめてから実行します。

# おわりに

第46部で、アラートの中身を値を見ずに調べ、LLM に渡す項目を決めました。

| 項目 | 結果 |
|---|---|
| アラート | 245件（多くは PAM・SSH・Proxmox の認証の記録。Level 7 の17件は PostgreSQL の ERROR） |
